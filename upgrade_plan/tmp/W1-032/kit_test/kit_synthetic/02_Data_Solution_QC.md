# Gate 02 - Data, Environment & Solution QC

The files under review are `environment/` (Dockerfile + `data/`) and `solution/` (solve.sh, solve.py, TRUTH.md) of one input bundle. To judge them you also open, read-only, `instruction.md` (DS-3, DS-10, DS-19, DS-20, DS-21, DS-25), `task.toml` (DS-14, DS-25), `tests/test_output.py` with its weight registrations (DS-15, DS-22, DS-24, DS-25) and `tests/judge.toml` (DS-17, DS-22). Your findings are still about the data, the environment and the solution (TRUTH.md included); defects inside those other files belong to their own gates. If you were not given the bundle path, ask for it and stop.

**Read TRUTH.md last, and only after you have formed your own DS-21 judgement.** TRUTH.md is the author's worked answer: it names the intended defect, the traps and the solution. Read first, it tells you what to see and you will see it, and a task that is actually unsolvable will read as solvable because the answer was handed to you. So work DS-1 through DS-21 from the agent-visible material on its own, write down what you concluded, and only then open TRUTH.md to check whether it agrees. Use it to verify, never to orient.

There is no script for this gate alone; `structure_qc.py` already verified the tree, the environment/ layout, and dash sweep. Your job is semantic: is the data right for THIS task, does the container actually support the task, and does the oracle actually solve it.

One check here does lean on a script number. DS-24 quotes the oracle-versus-verifier overlap that `tests_qc.py` reports (its oracle-overlap line). If you already have that output, read the number off it. If you do not, run `python3 tests_qc.py /path/to/bundle` and take it from there. Either way the number only tells you where to look; DS-24 is decided by reading the two files.

## Mindset

The data folder is the world the agent lives in. It must be necessary (task unsolvable without it, DS-2), referentially complete and truthful (everything the instruction points at is really there and the claims about it are true, DS-3), enough to actually solve the task (DS-21, the one that matters and the one DS-3 does NOT give you), and clean (nothing leaks the answer, DS-4). The Dockerfile decides solvability too: a single missing binary makes an otherwise perfect task score zero for every honest agent. The solution is the proof the task is solvable; treat it as evidence, not decoration.

## environment/ rules

- DS-1 All input lives in one or more input directories under environment/ (any names: data/, repo/, fixtures/...), each holding at least one file and each copied into the image by environment/Dockerfile; environment/ holds only the Dockerfile and those directories. The names and the split are the task's choice: judge only that each directory is a coherent unit of input (a repository, a corpus, a set of rule files), not that it is called data/. Script-owned, here for context.
- DS-2 Necessary: deleting the input directories must make the task unsolvable, and so must deleting any single one of them. If the agent could complete the task without ever opening an input directory, that directory is residue - fail.
- DS-3 Referentially complete and truthful: every data file the instruction references exists here with the exact name; every claim the instruction makes about the data (counts, formats, fields, examples) is true of the actual bytes. Open the files and verify, never infer from file name only. Note this is a much weaker property than the data being enough to solve the task, which is DS-21. A bundle can pass DS-3 cleanly and still be impossible.
- DS-4 NO ANSWERS IN DATA - strict, no exceptions. Nothing in any environment/ input directory may contain, encode, or make trivially derivable the expected final output of the task. A `*.solution.*` file, an answer key, a "labelled" file whose labels are the graded output, expected-output examples that the tests grade against - all fail. (Known real case: cache-adversary-synthesis shipped example_1.solution.json - that was a confirmed leak.) What is NOT a leak: a document describing the format, schema, protocol or rules the agent must work to. Contract material tells the agent what shape the answer takes; it does not hand over the answer, and a prompt is allowed to point at such a file instead of restating it (IN-8). So do not report one merely for existing. Read it before deciding, because the line is about content and not about the file being called a specification: a worked example carrying the graded values, a table of expected outputs, a walkthrough that computes a graded result, or prose stating the answer to a case anything grades is a leak whatever the document is titled. Confirm the answer genuinely is not recoverable by reading it, then move on.
- DS-5 No template residue (read every TODO/FIXME/XXX/PLACEHOLDER hit in context yourself; whatever the script reports on those markers is a lead, not a verdict): a partial spec with "(redacted)" sections, generic sample_NNN/field_NNN corpora, or any file that reads as boilerplate from another task is a fail. The known-bad inherited pattern is a `<TAG>-v1.0-DRAFT.md` spec with redacted sections - its presence is an automatic fail. Data must be curated for this task per the task guidelines.
- DS-6 Data files must make sense for the task story: formats parse, sizes are reasonable, damaged files are damaged on purpose (and the instruction says so).
- DS-7 No em/en dashes in text data files (script-checked bundle-wide; re-verify any file the script skipped as binary if it is actually text).

## environment/Dockerfile rules

- DS-8 Must never COPY tests/ or solution/ content into the agent image, in any form.
- DS-9 Must copy every input directory into the image at the path the instruction uses (conventionally /app/<dir>, e.g. /app/data, /app/repo), and the instruction must use those paths consistently.
- DS-10 Solvability: every tool, interpreter, package or library that the instruction or the reference solution needs must be installed by this Dockerfile. Compare the instruction's demands and solve.sh/solve.py imports line by line against what the image installs. A named-but-missing tool is a fail.
- DS-11 Offline contract respected. `[environment] network_mode` is pinned to `"no-network"` for every task, so this is not a value to read and compare: assume no network and check that every layer can live with it. Everything the agent needs must be baked in at build time, and any runtime fetch is a fail - `pip install`, `apt-get`, `npm i`, `git clone` or `curl` reached for inside the task flow, in the instruction, or in the ORACLE's own path. Pay particular attention to the oracle: a `solve.sh` that installs a dependency it needs will simply fail at grade time, and a bundle whose own reference solution cannot run offline is broken rather than merely fragile. The `[verifier]` and `[agent]` network lines govern the judge and the agent harness reaching their models; they are not this check's business and do not license anything in the task flow. If the task genuinely needs an outside endpoint to be solvable, report that as a design finding against the offline contract.
- DS-12 No secrets, no host paths, no `--privileged` assumptions, nothing that only works on the author's machine.
- DS-28 Every artifact directory is writable by the agent user. `[agent] user = "1000:1000"` runs the agent, and the oracle's `solve.sh`, as uid 1000, not root. The directory each declared artifact is written into must be owned by uid 1000 (or world-writable) in the image this Dockerfile builds, for example `RUN mkdir -p /app && chown 1000:1000 /app` before `COPY data /app/data`. COPY and ADD write root-owned files unless they carry `--chown`, so a `chown` placed before a COPY into the same directory does not cover it. A root-owned output directory makes the oracle die with `PermissionError` before it writes anything, and Step 10 reads 0.000. Fail. structure_qc S8 replays the Dockerfile's `mkdir`, `chown`, `chmod`, `COPY --chown`, `WORKDIR`, `USER` and `useradd -u` lines and checks the mechanics; you confirm anything it cannot see, such as ownership set by a script the Dockerfile runs, a base image's own users, or an `ENTRYPOINT` that changes permissions at start.
- DS-29 The openhands-sdk agent runtime is pre-baked. The harness runs the agent through the openhands-sdk wrapper from `/opt/openhands-sdk-venv`, and it only installs that runtime itself, over the network, when the venv is missing. With `[environment] network_mode = "no-network"` that install cannot run, so the agent never starts. Every `environment/Dockerfile` must therefore carry, in its final stage: the system packages `curl`, `ca-certificates` and `tmux`; a venv at exactly `/opt/openhands-sdk-venv`; `openhands-sdk==1.55.1 openhands-tools==1.55.1 litellm==1.105.0 fastapi` installed into it (those exact pins; fastapi unpinned; litellm 1.106.0 fails to import alongside the mcp package openhands pulls in); a build-time `/opt/openhands-sdk-venv/bin/python -c "import openhands.sdk"` so a broken install fails the build; and `chmod -R a+rX /opt/openhands-sdk-venv` so uid 1000 can run it. The recommended block, matching the harness's own installer:

  ```dockerfile
  # anubis: pre-baked agent so a sealed (no-network) run can start the agent.
  RUN apt-get update && apt-get install -y --no-install-recommends \
          curl ca-certificates tmux \
      && rm -rf /var/lib/apt/lists/*
  RUN curl -LsSf https://astral.sh/uv/install.sh | sh \
      && . "$HOME/.local/bin/env" \
      && uv venv /opt/openhands-sdk-venv --python /usr/local/bin/python3.12 --clear \
      && . /opt/openhands-sdk-venv/bin/activate \
      && uv pip install openhands-sdk==1.55.1 openhands-tools==1.55.1 litellm==1.105.0 fastapi \
      && /opt/openhands-sdk-venv/bin/python -c "import openhands.sdk, openhands.tools" \
      && chmod -R a+rX /opt/openhands-sdk-venv
  ```

  Any other install style that delivers every piece is equally correct and is not a finding, for example `python3.12 -m venv /opt/openhands-sdk-venv` followed by `/opt/openhands-sdk-venv/bin/pip install --no-cache-dir openhands-sdk==1.55.1 openhands-tools==1.55.1 litellm==1.105.0 fastapi`, or the apt packages folded into the image's main `apt-get install` line. Fail when a piece is missing or a pinned package carries another version or no version. structure_qc S9 checks each piece; you confirm the block sits in the final build stage and is not undone later (a later `rm`, a `chmod` that removes read access).
- DS-30 The uid 1000 agent account exists. `[agent] user = "1000:1000"` runs the agent and the oracle as uid 1000, so the final stage of `environment/Dockerfile` must create that account with a home directory and point `HOME` at it; without them, tools that write under `$HOME` (uv, pip, the agent itself) fail. Put these right after `FROM`:

  ```dockerfile
  RUN groupadd -g 1000 agent && useradd -u 1000 -g 1000 -m -d /home/agent -s /bin/bash agent
  ENV HOME=/home/agent
  ```

  structure_qc S10 fails when no `useradd`/`adduser` with uid 1000 exists, when that account has no home (`-m` / `--create-home`), or when no `ENV HOME=` is set. You confirm the account is not removed later and that a base image does not already own uid 1000 under another name.

## solution/ rules

- DS-13 solve.sh exists and is the entrypoint. solve.py is optional; if absent, solve.sh alone must carry the full solution.
- DS-14 The oracle must genuinely do the work: read the inputs, compute, and write every declared artifact to the exact paths the instruction promises. An oracle that copies a prebaked answer into place without computing it is a fail (it proves nothing about solvability and hides broken tasks).
- DS-15 Walk through solve.sh mentally against the tests: would it plausibly score 1.0? Every artifact produced, formats matching what tests expect, edge cases the tests grade actually handled. If you can name a test it would fail, that is a fail.
- DS-16 The oracle MAY read environment/ (allowed - it runs in the agent container where the input directories exist).
- DS-17 The oracle must never read or reference tests/ (test_output.py, judge.toml, reward.toml) - an oracle that peeks at the grader is a fail.
- DS-18 Idempotency: running solve.sh twice should not corrupt the result - warn only.
- DS-19 Stack conformance: solution code must respect constraints the contract imposes on the agent (stdlib-only, specific language, which files may be touched, which tool to use, what to leave alone). A rule of engagement counts when it is stated in a sentence the agent can read, in the instruction or in any file inside the input directories `environment/Dockerfile` copies into the agent image, so open those files too: a rule may live there rather than in the prompt. If the contract binds the agent to constraints the oracle itself violates, flag it.
- DS-20 The oracle obeys the contract, independently of the tests. Passing every test (DS-15) is NOT proof: tests undercover, and an oracle can score 1.0 while violating a stated rule no fixture happens to trigger. Walk the oracle's logic against every rule the contract states, wherever that rule lives, including rules no test exercises. Ordered logic deserves special care: when the contract states a precedence or tie-break chain ("check A before B before C"), read the oracle's actual check order and compare it pairwise against the stated chain. The oracle is the ground truth of the task; when it disagrees with the contract, every agent that obeys the prompt gets punished for the oracle's bug. Any divergence between stated rule and oracle behaviour is a fail, even when no current test would catch it.
- DS-24 The oracle is an independent implementation, not a copy of the verifier. Open `solution/solve.py` and `tests/test_output.py` side by side and judge whether the oracle solves the task or merely re-runs the grader's own code. tests_qc measures shared substantive lines, fails at 35% and warns from 20%, but the number is only a prompt to look: a small shared block can be the whole answer, and a large one can be incidental. This matters because a copied oracle is guaranteed to score 1.000. It cannot disagree with the grader, so the Step 10 oracle run returns a green light while proving nothing about whether the task is solvable at all. Two independent implementations only agree when both are right, and that agreement is the only evidence the oracle run actually produces. Some sharing is legitimate. A verifier that must generate a corpus needs an encoder, and the oracle needs one too. What is not legitimate is the oracle importing, copying or restating the logic that decides the grade. Ask which part of the shared code is the thing being graded: if the answer is "the shared part", the oracle proves nothing and this is a fail. Keep overlap as low as the task allows even when it is under the limit, and say so when you see an author sitting just beneath the line.
- DS-21 Solvable from what the agent actually receives. This is the mirror of DS-2: DS-2 asks whether the data is needed, this asks whether it is enough. Close `solution/` and `tests/` in your head and hold only what the agent holds, which is `instruction.md` plus everything under `environment/`. Nothing else reaches the agent. One question: could a determined expert, given unlimited time and skill and nothing but those files, actually arrive at the graded answer? If yes, this check passes, however brutal the task is. Difficulty is the point and it may come from anywhere. Traps, deliberately misleading surfaces, rules that only show themselves under one specific condition, data scattered across many files, a value in one file that only makes sense once another file is understood, chains where each step unlocks the next, edge cases that punish a naive reading, long grinding search. None of that is a defect and none of it belongs in your report. Working it out is the agent's job, and a task that gives up its answer easily is a worse task. The defect is different in kind: information the agent needs that exists in none of its files and follows from nothing in them. The clearest case is a value the agent must reproduce exactly while nothing it can see constrains or confirms it, such as a secret key, a private label, or an arbitrary constant taken from the author's head. There the agent has nothing to reason from and no way to tell a right guess from a wrong one, so skill stops mattering and the task is impossible rather than hard. Default to pass. To fail this check you must do two things: name the exact piece of information the solver cannot obtain, and show that it appears in no agent-visible file and follows from nothing in them. If you cannot do both, the task is hard, not impossible, and it passes.
- DS-25 The exact output shape is reachable. DS-21 asks whether the agent can work out the answer; this asks whether it can work out what the answer has to look like. They fail separately, and this one fails silently, because an agent can compute every value correctly and still score zero for emitting them under names it had to invent. Do it mechanically. List every literal the grading side requires of the agent's output: JSON key names, section headings, CSV column names, error strings, enum values, filenames the tests open, ordering the tests assume. Read them out of `tests/test_output.py` directly rather than trusting a summary, and include the ones built at runtime rather than written as constants, since string formatting hides them from any search. Then for each one, find where the agent could learn it: the instruction, a specification or schema file under `environment/`, or the shipped data itself, including the interiors of any archive the agent is given. Name the file for each. Any required literal that appears in no agent-visible file is a fail, because no amount of skill produces a name nobody supplied. Report the count and the specific names, for example "18 of 24 required keys appear in /app/data/SCHEMA.md, these 6 appear nowhere". A shape the agent must invent and the grader then insists on is the single most common way a solvable task becomes unpassable.
- DS-26 Nothing that gives away the answer is reachable anywhere in the agent image. DS-4 covers `environment/`, which is where reviewers look. This covers everywhere else, because the agent has a whole filesystem and the instruction only points at part of it. Read `environment/Dockerfile` line by line and follow what each step leaves behind. Check for: a COPY or ADD that lands solution material outside /app/data, a RUN step that writes a worked answer, an expected output or a reference artifact into `/tmp`, `/root`, `/opt`, `/usr/local` or the image's working directory; a build stage that produces the answer and is then copied from; a package, wheel, git checkout or archive whose contents include the solution; a leftover script, log, cache or history file from building the broken state. Bind mounts and volumes count too. Fail on anything from which the answer can be recovered without doing the work, and say exactly where it lives and how the agent would reach it. The test is not whether the file looks like an answer; it is whether an agent that finds it can shortcut the task.

## TRUTH.md rules

`solution/TRUTH.md` is required. It is the author-side golden trajectory: eight sections (Defect, Load-bearing work, Verification, Root cause, Solution shape, Ordered plan, Pitfalls, Provenance) that record what the task breaks, what the solver must work out, and how grading answers it. It is never shipped into any container. Open it only after DS-21, per the note at the top of this gate.

- DS-22 TRUTH.md describes the bundle that actually shipped. This is the one thing no script can check: a digest comparison proves `solve.py` was not edited after the fact, but nothing proves the prose still describes the code. Read the `Root cause` and `Solution shape` sections against `solution/solve.py` and confirm they describe the same mechanism, not an earlier draft of it. Read the `Verification` section against the weight registrations in `tests/test_output.py` and the criteria in `tests/judge.toml` and confirm the stated counts, weight totals and named negatives are the real ones. Read the `Defect` section against the task and confirm each item marked focal, drift or trap really is one: a "trap" nothing in the data can spring, or a "focal" item no test grades, is a claim the bundle does not honour. A TRUTH.md that describes a different task, a superseded solution, or grading that does not exist is worse than none, because reviewers after you will trust it. Fail, and name the section and the contradiction. Any sha256 line in TRUTH.md that does not match its file is a fail, not a minor.
- DS-23 TRUTH.md is invisible to the agent. Confirm `environment/Dockerfile` copies only what the agent needs and never reaches outside `environment/` (structure_qc S7 checks the mechanics; you check intent, including a copy that reaches it by a wildcard or a build stage). Note that `solution/` now carries the whole answer twice, the oracle and TRUTH.md, so any route into it is a double leak. Confirm `instruction.md` never mentions TRUTH.md, since naming it tells the agent an answer document exists and invites a hunt for it. Any route by which the agent could read this file is a fail: it is the complete answer, so one leaked copy makes the task free.
- DS-27 TRUTH.md describes the task, not how the task was made. It is a client delivery file. Its job is to state what the task breaks, what the solver must work out and how grading answers that, so a reader who has never seen the bundle understands the task itself. What does not belong is any narrative of the production process: how the bundle was generated, an archetype or template name, a generator seed, tooling or model credits, a changelog of what the author tried first, "this was built by" or "I then added", review and approval history, internal taxonomy. None of it describes the task, and shipping it hands the client a record of our process in place of a description of the work. The `Provenance` block is not an exception. Identifiers and digests belong there, because that is bookkeeping binding the document to the shipped bytes. Authoring attribution does not, and neither does anything naming the tool that produced the bundle. Generated bundles carry an `authored_by` value emitted by the generator; it is stale template output, it says nothing true about who built this task, and it ships to the client. Treat it exactly as you would the same claim in prose: it comes out. Fail on process narration and on authoring or tooling attribution, naming the section and quoting the line.

## Severity guide

fail: DS-2, DS-3, DS-4, DS-5, DS-8, DS-10, DS-11, DS-12, DS-14, DS-15, DS-17, DS-19, DS-20 violations; DS-9 when the instruction and image disagree on the data path (solvability break); DS-21 information the solver needs that is unreachable from every agent-visible file, making the task impossible not hard; DS-22 TRUTH.md contradicting the shipped solution, the real grading, or its own defect classification; DS-23 any route by which the agent could reach TRUTH.md; DS-24 an oracle whose graded logic is the verifier's own code; DS-25 a required output literal that appears in no agent-visible file; DS-26 any answer-revealing artifact reachable in the agent image; DS-27 authoring or process narrative in TRUTH.md. minor: small data inconsistencies with no grading impact, cosmetic Dockerfile issues. warn: DS-18, style choices, judgment calls you want the tasker to see.

Report in the fixed output format defined in the "Output format (all gates)" section of Final_checklist.md, then stop.
