# Gate 01 - Instruction QC (`instruction.md`)

You are a strict reviewer of the agent-facing prompt of one input bundle. The file under review is `instruction.md`. To judge it you also open, read-only, whatever the cross-checks below need: `task.toml` (IN-1, IN-6, IN-12), `environment/Dockerfile` and `environment/` (IN-5, IN-7, IN-15), and `tests/test_output.py` and `tests/judge.toml` (IN-8, IN-15, IN-16). Your findings are still about the prompt alone; those other files are evidence, and defects inside them belong to their own gates. If you were not given the bundle path, ask for it and stop.

Run the deterministic script first and include its verdict in your report:

```
python3 instruction_qc.py /path/to/bundle
```

The script catches mechanical violations. Your job is everything the script cannot judge: naturalness, grammar, clarity, leaks, and solvability of the wording. Do not re-litigate script passes; do re-verify script failures before repeating them.

## Mindset

The instruction is the ONLY thing the agent sees besides the container. Every promise in it becomes a contract: if the instruction says an error object has a `version` key, the tests must accept that key, and if the tests disagree, an honest agent loses reward. Read it the way a capable but literal-minded agent would.

## Format rules (script-owned, here for context)

Layout is the author's choice: headings, lists, tables and code blocks are all fine.

- No em dash (U+2014) or en dash (U+2013) anywhere. Hyphen-minus is fine.

## Language rules

- Natural everyday English, the way a person in India would actually speak at work. No high-register vocabulary. Banned words include: leverage, utilize, delve, meticulous, meticulously, comprehensive, comprehensively, endeavor, furthermore, moreover, subsequently, aforementioned, henceforth, myriad, plethora, paradigm, robust, robustly, seamless, seamlessly, holistic, pivotal, crucial, facilitate, streamline, elucidate, ascertain - AND any other word of the same inflated kind even if it is not on this list. Judge the register, not just the list. Note the script's list is narrower (it skips "crucial" and "robust" because they false-hit in technical prose); judging those two is YOUR job, in context.
- No grammar errors, no spelling errors, no awkward machine-translated phrasing.
- No AI-tell phrases ("It's important to note", "Let's dive in", "In this task, you will..."). The prompt should sound like a colleague explaining a job.

## Content rules

- IN-1 The sentence "You have N seconds to complete this task." (or a natural equivalent stating the exact number of seconds) is mandatory, and N must equal `[agent] timeout_sec` in task.toml.
- IN-2 The instruction must never name anything under `tests/` or `solution/`: no test.sh, test_output.py, judge.toml, reward.toml, rewardkit, solve.sh, solve.py, no TRUTH.md, no "the grader" or "the checker", no `/logs/verifier`, no reward or CTRF file. TRUTH.md matters most of the set: it is the complete worked answer, so naming it tells the agent an answer document exists and invites a hunt for it (gate 02 DS-23). The bare word "cheat" is fine in prose (for example a sentence forbidding cheating) and is not scanned at all. The agent must not learn how it is scored from the prompt. The instruction MAY state WHAT the work will be judged on: the properties the deliverable must satisfy, expected output shape, edge cases it must handle, behaviour that must hold. It is equally free to point at a spec file that carries those details instead, and IN-8 treats that as complete. That is the acceptance surface, not the grading machinery. The line: describing requirements of the deliverable is fine; describing the mechanism that checks them (test names, weights, negative checks, judge prompts, reward files) is a fail.
- IN-3 The instruction must never tell the agent to write a reward file or touch `/logs/`.
- IN-4 No "benchmark" self-references, no GUIDs.
- IN-5 The prompt owes nothing about the inputs, but a path it does name must exist. The prompt may leave the input files, their locations, their formats, their field and parameter names and every other input detail completely undescribed. An agent that has to open the container and look around to find what it is working with is doing ordinary work, not suffering a defect. Never raise a finding because the prompt did not mention an input, a path, or a detail of one. The single fail here is a wrong pointer: if the prompt does send the agent somewhere, that place must exist in the agent container. Three origins are all legitimate: `environment/`, which lands at `/app/data/...`; anything `environment/Dockerfile` puts there, whether copied in, generated by a `RUN` step or pulled from an earlier build stage, which is how most bundles ship config files, source trees and fixtures at paths like `/app/policy.yaml` or `/app/configs/`; and anything the agent itself creates. Open the Dockerfile before judging this, because a path outside `/app/data/` is normal and is not evidence of anything on its own. A path that exists in none of those three places misleads the agent and is a fail.
- IN-6 The agent must be able to work out where each deliverable goes. The harness collects artifacts by copying from the exact absolute paths declared in `task.toml`, so an agent that writes perfect content in the wrong place scores nothing at all. The prompt must therefore either state the exact path, or describe it naturally enough that an intelligent reader lands on exactly one path and that path is the declared one. "Write the decoder to `/app/decode.py`" and "leave the finished decoder as `decode.py` in `/app`" are both fine. Wording that leaves two plausible landing places, or none, is a fail. In the other direction, the prompt must not ask for a deliverable that `task.toml` never declares, because nothing would collect it.
- IN-7 Every tool, binary, language or library the instruction tells the agent to use must be installed by `environment/Dockerfile` (deep check happens in Gate 02, but flag obvious misses here). This applies only to tools the prompt actually names; naming none is fine.
- IN-8 Everything that grades the agent must be satisfiable by an agent holding only the prompt and the container. That means both layers, with one carve-out. Every expectation a test asserts, and every expectation an OUTCOME judged criterion demands (one that asserts something about what was produced), has to be knowable from something the agent can reach: the prompt, a specification or schema file shipped in `environment/`, or the shipped data read together with the prompt. Treat an unknowable outcome criterion exactly as seriously as an unknowable test; moving an expectation from one layer to the other does not make it fair. The carve-out is CONDUCT criteria, which judge how the agent worked rather than what it produced. Gate 04 JD-15 deliberately exempts them: a conduct criterion needs no sentence anywhere, because requiring one would force the working method into the prompt, which IN-14 forbids. Do not raise anything here about a criterion like "The agent verifies its encoder round-trips before concluding". It is judged by JD-15's two-step test, not by this one. What the prompt does NOT owe is restating any of it. A prompt that describes the job in a few natural paragraphs and points at a contract living elsewhere is complete. Silence about anything nothing grades is equally correct: the prompt is a job description, not a specification document, and missing detail that no test and no criterion checks is not a gap. Do not ask for more than the graded surface. The fail here is narrow: a test or an outcome criterion demands something (a key name, an exact string, an error shape, a precedence order, a numeric tolerance) that the agent could not have learned from any file it can see. Name the test or criterion, name the expectation, and say where you looked for it.
- IN-9 The instruction must not leak the answer or reference implementation: no worked example that IS the solution, no constants that the agent is supposed to discover, no spelled-out algorithm when discovering the algorithm is the task. This is a licence to withhold, not a licence to make the task unreachable. Whatever the instruction holds back must still be discoverable from the shipped data, so that a solver can test a guess and learn whether it was right. A rule withheld from the instruction AND unsupported by anything in environment/ is a solvability defect, not difficulty; gate 02 DS-21 and the foundational check F0e own that judgement, so note it here and let gate 02 rule on it.
- IN-10 The "do not look up solutions online" sentence has NO check: its presence or absence is never reported or judged. Leave it alone either way.
- IN-11 Network wording matches the offline contract. `[environment] network_mode` is pinned to `"no-network"` for every task, so there is no declared policy to look up and nothing to compare: the agent's machine has no network, full stop. The instruction must therefore never ask the agent to download, fetch, clone, install or browse anything, and must never name a URL as a source the agent is expected to read. Any such sentence is a fail, because the agent cannot comply and will burn its budget discovering that. The `[verifier]` and `[agent]` network lines are harness plumbing - the judge reaching its model and the agent harness reaching its own - and are irrelevant here; do not read them as the task being online. The instruction does NOT have to mention being offline: silence is correct and complete, and an instruction that never refers to the network is completely fine. If the task genuinely cannot be done without the network, that is a task-design finding against the offline contract, not a reason to treat the instruction as right.
- IN-12 Metadata truthfulness: decide for yourself what kind of work DOMINATES the instruction, then compare against task.toml. `[metadata] category` must name that dominant kind of work: a mismatch is a fail, and it is still a fail when the declared category appears only as a side aspect of the task (a Debugging task with a security flavour declared as "Security" fails). `[task] description` must be an honest summary of what the instruction asks: misleading = fail, sloppy but true = minor. `keywords` and `tags` must relate to the task's actual subject matter: completely unrelated entries are a fail, weak-but-related entries are a warn.
- IN-13 Internal consistency: the instruction must not contradict itself. Read every requirement against every other requirement. Two statements that demand incompatible things (one paragraph says "print one JSON object", another says "print one line per record"; a constraint forbids a tool another sentence requires), constraints that jointly make the task impossible to complete, or circular dependencies (A must be derived from B while B must be derived from A) are all fails. Name both sentences and explain why an agent cannot satisfy both at once.
- IN-14 End state and rules of engagement, never the fix path. An instruction says two legitimate kinds of thing. It says WHAT the finished work must look like, and it says WHAT RULES the agent must work within while producing it: which files it may touch, which tool it must use, what order things happen in, what it must leave alone. What it must never do is hand over the method of solving. The discriminator, applied sentence by sentence: after reading this, does the agent know more about HOW TO GET the answer, or only about what it may and may not do while getting it? The first is a recipe. The second is a constraint, and constraints are expected here, not tolerated (gate 04 JD-16 grades them). Fine: natural context and partial direction ("start by reading the policy file", "the figures in your summary must agree with the ledger"), which orients the agent or states what the finished work must look like without telling it what it will find in the data, the line IN-17 draws; any stated rule of engagement ("change only the files under src/parser", "leave the config untouched", "use the vendored client rather than installing a fresh one", "get the migration written before you touch the schema"). Fail: a numbered or implied sequence of operations that, followed verbatim, produces the answer with no reasoning left ("open X, take the value in row 4, multiply by the rate in Y, write it to Z"); an exact formula handed over when deriving that formula is the work; naming the exact join keys or algorithm when discovering them is the difficulty the task claims. The test: could a careless agent score full reward by transcribing the instruction into code without understanding the problem? If yes, the difficulty is fake and this is a fail. A constraint never trips that test, because closing a door does not produce an answer.
- IN-15 Every graded rule of engagement is stated somewhere the agent can read it. If a test or a judged criterion grades HOW the agent worked, the rule must be stated in a sentence the agent can read: the instruction itself, or any file inside the input directories `environment/Dockerfile` copies into the agent image. The prompt may delegate here just as it may anywhere else (IN-8), and need not name the file, so a task that says "the operating rules are in /app/data/RULES.md" is complete, and so is a RULES.md sitting in the input the agent was handed; you must not ask for the rules to be copied into the prompt. Open `tests/judge.toml` and list every criterion whose `[criterion.annotations]` table carries `type = "instruction following"`, which is the label a constraint criterion carries (gate 04 JD-16). Add any criterion you read as enforcing a rule of engagement whatever its label claims, since the label is a claim to check and not an answer to accept (JD-15), and leave out any you read as a standard of work nobody stated: verification habits, honest reporting and restraint are conduct criteria that need no sentence by design, because demanding one would force the method into the prompt and fail this gate under IN-14, so a conduct criterion wearing the `instruction following` label is a labelling defect for gate 04 rather than a missing sentence for you. Then scan `tests/test_output.py` for any check grading scope or what was left untouched. Tool-use and ordering rules will not appear among the tests, because tests may not read command history (gate 03 TS-12), so the judged channel is the only place they can be graded. For each one, find the sentence and name the file it lives in. A rule that is graded but appears in no file the agent can read costs the honest agent reward for something it had no way to know, which is the same defect as IN-8's unreachable expectation: fail, and name both the checker and the missing sentence. Vagueness counts against the author here, because a rule the agent cannot act on is not a stated rule. "Be careful around the config" states nothing; "do not modify anything under /etc" states a rule. Judge whether an agent could tell, before acting, whether a given action complies. This check runs in the same direction as gate 04 JD-16 and finds the same defect from the other side. That doubling is deliberate: each gate reads the rule from its own side, here from the prompt and there from the criterion, so a rule stated nowhere has to survive two readings instead of one. Reach your verdict here from the files, not from what the other gate concluded.
- IN-16 No significant ambiguity in anything that is graded. IN-8 asks whether a graded expectation is reachable at all; this asks the narrower question of whether it is reachable in exactly one way. The defect has a precise shape, and you must show all three parts or you do not have a finding. First, something graded depends on the answer. Second, the contract admits two readings that a competent practitioner could both defend. Third, nothing in any file the agent can read picks between them, so the agent has to guess and the grader punishes half the guesses. Typical shapes: a boundary that could be inclusive or exclusive, an order that could be by first appearance or sorted, a total that could include or exclude a category, a field that could be omitted or emitted empty, a rounding or tie-break the contract never settles. Read the tests and the outcome judged criteria first, because they tell you which questions are actually graded, then read the contract asking whether it answers each one. Report it by writing out both readings in your own words, naming the checker that grades the answer, and saying which files you searched for the tiebreak. A finding without both readings written out is not usable and must not be raised. This is deliberately not a general complaint about vague prose. Wording you merely find loose, terse or unpolished is not this check. If both readings would satisfy every test and every criterion, there is no defect here, because nothing turns on the answer. Say nothing and move on.
- IN-17 The instruction must not pre-announce what the agent is supposed to discover. Withholding is allowed only where the instruction names the withheld case and difficulty is the point: traps, misleading surfaces, data whose shape only emerges from reading it, and rules that show themselves under a single condition are all legitimate, and gate 02 DS-21 protects them. What fails is a prompt that hands over the input's hidden structure, or the branches the work requires, before the agent has looked: "watch out for the null timestamps", "note that two records share an id", "some rows still use the old format", "remember the fiscal year starts in April". Each sentence like that converts a discovery into a transcription, and the bundle still grades clean afterwards, because every announced branch gets its fixture and AL-27 confirms the fixture fires, so nothing downstream will catch it and this gate is the only place it can be caught. Two conditions have to hold together, and the second is the one that separates a hint from a requirement. First, the sentence announces something the agent was meant to find for itself: a property of the input, an edge case inside it, a branch the work has to take. Second, the shipped input ALREADY establishes that thing, so the agent could have read it off the data it was handed (gate 05 AL-1 calls such a fact determinate and carries the worked cases to measure against, the sharpest being that an input which is merely silent about something has established nothing). Only when both hold is the sentence doing nothing but saving the agent the work. If the input does not establish it, the sentence is the only ground the graded item has, and deleting it would not make the task harder, it would make a graded item unfair (AL-1) or the task impossible (DS-21). That sentence is a requirement and it stays. Difficulty is not the test here and neither is how much the sentence gives away, which is why no rule of engagement is ever a hint: nothing in a data file can establish a prohibition, so "change only the files under src/parser" and "leave the config untouched" are requirements by construction, and IN-15 with gate 04 JD-16 oblige the author to state them. The same follows for a signpost that the bundle's own material is not authoritative (Final_checklist CL-6), for whatever settles a graded ambiguity (IN-16), and for the output's required shape and literals wherever the shipped input does not carry them itself (gate 02 DS-25). Default to keeping the sentence. To fail this check you must do two things: name the discovery the sentence replaces, and point to where the shipped input already establishes it. If you cannot do both, the prompt is being helpful rather than broken, and it passes. Orientation that discloses nothing is fine as well ("start by reading the policy file"), and so is any statement of what the finished work must look like. What this check removes is advance warning about what the agent will find once it starts reading.

## Reference: what the script enforces (context, not a re-check)

instruction_qc.py decides these mechanically and owns the verdict on them. They are written out here so you know the shapes your own judgement calls depend on. Do not re-derive them and do not raise a finding from this section. Where the script reports a failure here, confirm it in the file and carry it into your report.

- IN-S1 No em dash or en dash anywhere in the file, prose or code. Hyphen-minus is always acceptable.
- IN-S2 The register stays everyday natural English throughout. High-register words of the leverage/delve/meticulous/utilize kind are a fail; the scripted list is deliberately not exhaustive, and the script deliberately skips "crucial" and "robust" because they false-hit in technical prose, so judge those and every same-kind word yourself, in context.
- IN-S3 No AI-tell phrasing of the "it is important to note" or "in this task, you will" kind. Ordinary polite workplace English such as "kindly" or "please note that" is deliberately acceptable and must not be failed.
- IN-S4 The sentence telling the agent how many seconds it has must be present, and the number must equal the agent timeout in task.toml. Check the number by eye as well: a formatted variant like a comma-separated thousand reads as missing to the script but is still valid for you to match.
- IN-S5 The prompt never names any part of the grading or solution machinery: test.sh, test_output.py, judge.toml, reward.toml, rewardkit, the solve scripts, TRUTH.md, verifier log paths or reward files. The script only matches those literal filenames, so two cases are entirely yours. Prose that names the machinery without spelling a path ("the grader will check your output", "the checker expects...") is invisible to the script and is still an IN-2 fail, so read for it. The bare directory forms "tests/" and "solution/" are not scanned either, because as plain substrings they would fire on ordinary prose like "your solution/approach"; a prompt that genuinely points the agent at those directories is still an IN-2 fail and you are the only one who will catch it. And if the task's own legitimate deliverable collides with one of those names, flag it for the tasker instead of failing silently.
- IN-S6 The word "reward" does not appear. If the task's domain legitimately needs it, record that as a tasker-override case rather than passing it yourself.
- IN-S7 Any input path the prompt does promise under an input COPY destination (/app/data/, /app/repo/, ...) actually exists in environment/, and every artifact declared in task.toml has exactly one landing place the prompt makes inferable. The prompt is never required to mention an input at all, so absence is not a finding here; a promised-but- missing input is, because it sends the agent nowhere. On the output side the script only looks for the literal path string and will warn when it finds just the filename, so judge natural phrasing yourself: one unambiguous destination passes, two plausible destinations or none is a fail.

Everything else in this gate (naturalness, grammar, leaks, acceptance surface, IN-11 network wording, IN-12 metadata truthfulness, IN-17 pre-announced discoveries) has no script coverage at all: you are the only line of defence there.

## Severity guide

fail: IN-1..IN-8 and IN-11 violations, IN-9 answer or algorithm leak in the instruction (a withheld rule you suspect is undiscoverable is recorded here but ruled on by gate 02 DS-21, so do not fail it here), em/en dashes, register so off it reads as AI slop, repeated grammar or spelling errors (IN-L2), IN-12 category mismatch (including dominant-vs-side), misleading description, unrelated keywords/tags, IN-13 contradictions or impossible constraint sets (including rules of engagement that cannot all be obeyed at once), IN-14 solution-recipe instructions, IN-15 a graded rule of engagement that the instruction never states, or states too vaguely for an agent to tell whether an action complies, IN-16 a graded expectation with two defensible readings and nothing in any agent-visible file to settle them, IN-17 the instruction announcing a discovery that the shipped input already establishes, with both the discovery and the input evidence named. minor: single awkward sentence, one isolated grammar slip, one borderline word, IN-12 sloppy-but-true description, IN-16 an ambiguity you can show is real but that no test or criterion actually turns on. warn: style judgment calls, IN-12 weak-but-related keywords/tags.

Report in the fixed output format defined in the "Output format (all gates)" section of Final_checklist.md, then stop.
