# Gate 03 - Tests QC (`tests/`)

The files under review are the test channel of one input bundle: `tests/Dockerfile`, `test.sh`, `test_output.py` (the rewardkit criteria and their weight registrations) and `reward.toml`. (judge.toml has its own gate, 04.) To judge them you also open, read-only, `instruction.md` and the input directories `environment/Dockerfile` copies into the agent image (TS-17, TS-18, TS-19, TS-20), `task.toml` for the declared artifacts (TS-7), and `tests/judge.toml` for its positive weight total, which `reward.toml` divides by (TS-10). Your findings are still about the tests; defects inside those other files belong to their own gates. If you were not given the bundle path, ask for it and stop.

The shape every one of these files must follow is in the "Authoritative test channel templates" section of `Final_checklist.md` (test_output.py, reward.toml with how to read it, test.sh, tests/Dockerfile). This gate checks against those templates and does not restate them in full.

Run the deterministic script first and include its verdict in your report:

```
python3 tests_qc.py /path/to/bundle
```

The script handles the mechanical layer (check/registration bijection, weight scale, counts and balance, reward.toml arithmetic, forbidden reads). Your job is the semantic layer: do these checks grade the right thing, fairly, and uncheatably.

Throughout this gate a "test" means one rewardkit check in `test_output.py`: a top-level function decorated with `@criterion(description=...)`, taking only `workspace` and returning a bool, registered once at module level with `criteria.<name>(weight=W)`. rewardkit scores the module as the `test_output` input; `tests/reward.toml` combines it with the `judge` input into the one `reward`.

## Mindset

The tests ARE the task. An agent that satisfies the contract but fails the tests was robbed; an agent that games the tests without doing the work stole reward. Both are QC failures of the same root kind: the tests and the contract describe different tasks. A test is fair when what it reads is either promised by the instruction or determinate in the input the agent was handed, and the prompt does not have to point at the file that establishes it, since working out your own data is the task (TS-19). Read every test asking "what observable does this read, and could the agent have learned, from the prompt or from the input it was given, that this observable would matter?"

## The two-container rule (memorize this)

Grading runs in a fresh container built FROM `tests/Dockerfile` with `tests/` as the build context. No agent input path (`/app/data`, or wherever environment/Dockerfile COPYs an input directory) EXISTS there. Declared artifacts are uploaded to their exact declared absolute paths (e.g. `/app/decode.py`); the harness copies the declared path string verbatim, which is why task.toml artifacts must be absolute. Therefore:

- TS-1 Nothing under tests/ may unconditionally read an agent input path (`/app/data` or any other input COPY destination) at grade time. Guaranteed crash. Fail. Comments and docstrings that merely mention the path are fine (the script skips them), and a read behind an existence check or env override is safe (the guard falls through to a fallback when the path is absent) - not flagged.
- TS-2 `tests/Dockerfile` must `COPY . /tests/` (the image must own the test files: in separate mode Harbor 0.24.0 does not upload tests/ when tests/Dockerfile exists) and install exactly `harbor-rewardkit==0.2.1`, the version Harbor 0.24.0 pins. An unpinned, ranged or different version is a fail. The same line must pin litellm with `==` (the reference pin is `litellm==1.105.0`, what the agent image pins): rewardkit accepts `litellm>=1.83` with no upper bound, so an unpinned verifier takes whatever PyPI serves at build time, and a withdrawn litellm 1.107.0 stable shipped site-packages hooks that fetched and ran remote code in the container holding the judge key. Unpinned or a quarantined version is a fail; another exact version is a warn needing tasker approval.
- TS-3 `tests/Dockerfile` should `RUN mkdir -p /app` (reference-task convention). The harness auto-creates artifact parent dirs at upload time, so absence is a warn, not a crash.
- TS-4 `tests/Dockerfile` must install every third-party package test_output.py imports other than rewardkit (mind pip aliases: yaml/pyyaml, PIL/pillow, sklearn/scikit-learn) and every tool the scripts invoke (`util-linux` for `setpriv` or `runuser`), on Python 3.12 or newer, which rewardkit requires. pytest is not required. The agent image's packages are NOT available here.
- TS-5 Any ground truth the tests need (expected values, fixtures, generators) must live inside tests/ itself, never be read from agent-writable paths.

## test.sh rules

- TS-6 rewardkit writes the reward; test.sh writes none. test.sh follows the template: it clears stale reward files (`reward.txt`, `reward.json`, `reward-details.json` under `/logs/verifier`), locks the log directory, restricts `/tests`, and its last line is `exec rewardkit /tests --workspace /app --output /logs/verifier/reward.json`. rewardkit then writes `reward.json` and `reward-details.json` beside it. test.sh writes no reward bytes itself (no `echo` or `printf` into a reward file, no Python that writes one), runs nothing after rewardkit, and has no branch that skips it. If rewardkit fails, no reward.json exists and Harbor records a verifier error; that is the intended outcome for an authoring defect, and Step 10 makes such a bundle unshippable. Bad agent output must never be what makes rewardkit fail: that is TS-29. Trusting a pre-existing reward file is a fail. The same verifier error is also the intended outcome of a real agent run with no `OPENAI_API_KEY` (rewardkit raises "Missing credentials") or with no `/logs/agent/trajectory.json` (rewardkit raises "Trajectory not found"): a run whose judged half was never scored has no reward to report, so neither is a finding and neither may be worked around in test.sh. Step 10 avoids both by running the tests-only copy `exe_copy.py` builds.
- TS-7 Computes the reward exclusively from tests/ ground truth plus the uploaded artifacts. Never from anything the agent could have written outside the declared artifacts.
- TS-8 No skip switches (`SKIP_TESTS=1`, `if [ -f /app/skip ]`, env-var bypasses).
- TS-9 Never `source`/`exec`/import from agent-writable paths; not PATH-shadowable (does not rely on bare tool names resolvable to /app; absolute paths or controlled PATH).
- TS-10 `tests/reward.toml` combines the channels correctly. It holds exactly one `[[reward]]` table with `name = "reward"`, `aggregation = "weighted-sum"` and `weights` naming exactly `test_output` and `judge`, plus one `[scoring.test_output]` table with `aggregation = "weighted-sum"`, and no other keys or tables. `weights.test_output` equals 0.5 divided by the sum of positive weights registered in test_output.py, and `weights.judge` equals 0.5 divided by the sum of positive criterion weights in judge.toml, both written at full float precision (Python's `repr` of the division). Recompute both from the actual files. The final reward is then half of (test weight earned / test positive total) plus half of (judge weight earned / judge positive total): 1 when every positive passes and no negative fires, 0 for doing nothing, -1 at worst. No clamp exists anywhere and none is needed, because neither channel's negatives may outweigh its positives (TS-23, gate 04 JD-12). A weight left stale after a check or criterion changed is a fail: the score then stops running from -1 to 1. No other top-level `.py` file under tests/ defines criteria, no other `.toml` carries `[judge]` or `[[criterion]]`, and no subdirectory of tests/ holds either, since rewardkit would score each one as an extra input.

## test_output.py rules

- TS-11 Deterministic: the same submission must earn the same score every run. Step 10 runs the oracle five times and requires 1.000 each time, but that only catches drift that happens to show up in five tries. Reading catches the rest, so walk the tests hunting for each of these by name: wall-clock or date values in an assertion, including "today" and elapsed-time bounds; unseeded `random` or `uuid`; iteration over a `set`, or over a `dict` built from a `set`; `glob`, `os.listdir`, `os.walk` or `Path.iterdir` consumed without sorting; tests that depend on running in a particular order or that mutate state a later test reads; timing margins tight enough to lose on a slow machine; locale, timezone or default-encoding dependence; hash-order effects; any network call at all. Because reward here is weighted rather than pass/fail, a single flaky check worth 3 of 53 points does not flip the verdict, it just moves the number a little on every run. That is invisible in one run and it is exactly the noise that ruins a training signal, since the agent is scored for something it did not do. Name the specific line, not the general worry.
- TS-12 Outcome-driven: tests grade the final state and artifact behaviour, never the agent's command history or console output. This holds for stated rules of engagement too, and it decides which of them a test may own. In separate mode the verifier sees only the declared artifacts, so a test can grade scope or another effect only when the affected paths are declared artifacts; otherwise the judged channel owns it. A scope test that passes because something is absent is a negative (TS-25). A tool-use or ordering rule is not test material at all: proving it needs the command history, so the judged channel owns it, where the judge reads the trajectory (gate 04 JD-16). A test reaching into command history to check one is a fail even though the rule itself is legitimate. Where a test can grade a stated rule it should, since an assertion returns the same verdict every run and a judge does not, so a format, output-shape or declared-artifact scope rule left entirely to the judged channel is a real finding. Gate 04 JD-16 raises it, because deciding it needs the judged criteria in front of you; note it here if you spot it and leave the verdict to that gate.
- TS-27 Reading the agent's source is not proof the agent did the work. Any assertion whose subject is the text of a file the agent wrote, rather than what that file does when run, grades appearance instead of behaviour. The shapes to look for are `assert "token" in source`, a regex over source text, a check that some identifier or import is present, a line count, or a diff size. Names like `x_was_repaired_not_bypassed` are a strong hint, since a check that has to claim it is not being fooled usually is. These pay out for typing the right words. An agent that writes a stub doing nothing and mentions the expected identifiers in a comment passes every one of them, which is not a hypothetical: a stub with no working code has been measured scoring most of the available reward on a bundle built this way. Rewrite the check to run the thing and assert on the result: import the module and call it, execute the binary and compare output, feed an input that only works if the repair is real. Where the property genuinely cannot be observed by running (a licence header, a required file being present at all), keep the text check but weight it as the existence check it is, never as evidence the task was completed. A positive test that pays for source tokens is a fail. Say what a stub would score against it.
- TS-13 One property per test. A test asserting two unrelated properties hides which one failed and skews the weight; flag it.
- TS-14 Check names state the property: `<property>` for positives, `negative_<cheat>` for negatives, and the name and the `description` match what the body checks. The `negative_` prefix is used if and only if the registered weight is negative (the prefix-and-sign rule is script-owned; your part is whether the name and the description match what the body actually checks).
- TS-15 Negative checks use inverted polarity: the check returns True when the cheat is present, so an honest agent makes it return False and escapes the penalty; the negative weight does the punishing. Verify each negative check actually implements this direction; a check that returns True for honest work punishes honest agents. Each negative check should carry an inline comment stating the inversion.
- TS-16 Anti-cheat negatives must fire on the cheat and ONLY on the cheat. Ask for each: could an honest solution trip this? Could a cheater slip past it?
- TS-17 Comparisons are exact where the instruction promises exactness: byte equality, int equality, strict JSON equality. Watch the Python trap where `True == 1`: a bool/int confusion that lets `1` pass where `true` is required contradicts an exact-comparison promise - fail if the instruction implies strict types.
- TS-18 Tolerances, when legitimate (floats), must be stated in the instruction. A hidden tolerance, or a missing one that makes honest float output fail, is a fail.
- TS-19 Every graded behaviour must be learnable by the agent, and every promise the instruction makes must be graded by something. Learnable means stated in the instruction OR determinate in the input the agent is handed, meaning any directory `environment/Dockerfile` copies into the agent image; the prompt may delegate the detail rather than restate it and need not name the file, so read the shipped input before calling anything undocumented. A check grading a rule of engagement rather than a property of the deliverable is the exception: a check on what the agent left alone, or on which paths it touched, needs a sentence that states the rule, because discovery establishes facts and never prohibitions (gate 01 IN-15). On the coverage direction, do not demand that a test cover every promise: a promise may legitimately be graded by a judged criterion instead, which is common for things no assertion can decide. Flag a promise nothing grades at all, never one the judged channel handles. (The full cross-walk happens in Gate 05; flag obvious mismatches you see now, especially error-object shapes and extra undocumented error cases.)
- TS-20 Weights map to importance semantically. The scale means something: 5 = a core outcome, the deliverable's primary behaviour; 3 = an important sub-goal or key edge case; 1 = a minor detail or existence check. Negatives: -5 = a red-line cheat; -3 = a serious secondary violation; -1 = rare, minor. Judge every weight against what the test actually grades: a core-deliverable test carrying weight 1, or an existence/formatting check carrying 5, is wrong. Then check the ORDERING: if the instruction makes clear that property A matters more than property B, but B's test outweighs A's, the reward contradicts the task's own priorities - that is a fail, not a style call. Mild imbalance within the right ordering is a minor. All-identical weights are a fail (script).
- TS-25 Positive tests grade earned work, never an absence. Read every positive test's decisive assertion: if it passes because something bad is missing (an empty violations list, a banned import that is absent, output that "does not contain" a thing), it hands its points to any solver that simply did nothing wrong, and it inflates the positive total so every real test is worth proportionally less. Absence belongs on the negative side with inverted polarity: a `negative_<cheat>` check that returns True when the bad behaviour IS present, registered with a negative weight. A positive-weight check whose pass condition is an absence is a fail; keep the detection logic, move it to a negative check.
- TS-26 No intra-test double payment, in ANY pairing. Pair every test against every other test - negative against positive, positive against positive, negative against negative - and name the observable each reads. Two tests reading the same observable with the same decisive logic pay (or punish) one behaviour twice. Negative-vs-positive example: a positive test asserting output is identical across repeated runs alongside a negative test firing when output differs across runs is one determinism observation paid twice. Positive-vs-positive example: two tests that both decode the same fixture and assert the same field value is one correctness observation earning two weights, inflating that behaviour's share of the positive total. What is NOT a duplicate: two tests reading genuinely different aspects of the same object (the file parses; the parsed values are correct; the encoder round-trips it) - those add distinct signal. Same observable, same logic = keep one side, or rewrite one to read a different observable. Fail.

- TS-29 Checks never raise. Any exception inside a check aborts the whole rewardkit run, so no reward is written and an agent output that merely breaks one check turns into a verifier error instead of a score. Every read of agent output (open, parse, index, convert, subprocess) is guarded so bad, missing or hostile output makes the check return False; a negative check returns False unless the cheat is positively seen. Each check returns a bool, never a number, None or a string. Nothing at module level does work beyond defining constants, checks and registrations, because rewardkit imports the module. Trace each check against an empty workspace and against garbage in every artifact.

## Weight registration rules (script-owned, here for context)

- TS-30 Agent file modes are survivable. The oracle installs its program with `cp`, which leaves mode 0644; a real agent writes it through an editor that renames a temp file into place, so the same program arrives at 0600, owned by uid 1000. Harbor hands `/app` to the verifier with those modes intact, and the verifier runs as root, so reading the file is only a problem once a check drops privileges to run it (`setpriv --reuid=nobody`, `runuser`, or Popen `user=`). Then the unprivileged child cannot open the program, every check that executes it returns False on a perfectly correct submission, and the plain oracle run still reads 1.000, so nothing in QC notices until a real trajectory is graded and loses that whole tier. Any verifier that executes agent-written code under a dropped uid must make it readable first: chmod the program and the directories above it (root may), or run a copy the verifier staged itself. Relaxing or removing the privilege drop is not the fix; that trades this bug for TS-24. tests_qc H6 checks the three shapes statically and fails when it finds none; the proof is the `--owner-only` oracle run in Step 10, which reproduces the agent's 0600 modes and must still read exactly 1.000. A bundle that scores lower there is a fail. The owner's own execute bit survives that run (a file already executable becomes 0700, not 0600), so a check may require an executable artifact, but only when the instruction or an agent-visible spec says to make it executable; requiring a mode or a shebang nothing tells the agent about is a CL-5 hidden convention.
- TS-21 Exact bijection between check functions and registrations. Every check is registered exactly once, at module level, with `criteria.<name>(weight=W)`. An unregistered check is scored by rewardkit at the default weight 1 without anyone choosing that; a registration naming no check of this file pulls in a rewardkit built-in or crashes the run; a check registered twice is scored twice. The weight lives on the registration and nowhere else: `tests/test_weights.json` is forbidden (structure_qc S3).
- TS-22 W is an integer literal from {5, 3, 1, -1, -3, -5}. Zero, 2, floats (`5.0`), strings, a missing weight (rewardkit would default it to 1) and any other argument are all fails.
- TS-23 Counts and balance: at least 10 checks (fail), at most 40 (warn); at least one positive and at least one negative check (fail); weights not all identical (fail); the sum of absolute negative weights is at most the sum of positive weights (fail), so the test channel's share of the reward never drops below -0.5.

## Verifier execution isolation (only when tests execute agent code)

Grading runs as root in the verifier container, and most bundles execute the agent's own artifacts during grading (e.g. `python3 /app/decode.py`). That agent code is hostile input running with root privileges: it can fork a background process that waits for rewardkit to finish and then rewrites `/logs/verifier/reward.json` with 1.0, fake success codes, or tamper with the rewardkit process, inside which every check runs.

- TS-24 If any check in test_output.py executes agent-produced code, verify all of the following; any miss is a fail:
  - Agent code runs only as a subprocess with a timeout, started from inside a check, never imported or exec'd in the rewardkit process.
  - The subprocess output and exit code are fully consumed before the check returns; no pipe is left open to agent code.
  - Every agent subprocess has exited before its check returns (killing the process group), so nothing outlives rewardkit's final write.
  - Reason about survivability: could a daemonized child spawned by agent code outlive the run and rewrite `/logs/verifier/reward.json` afterward? If the answer is yes and nothing mitigates it, fail and describe the attack step by step.
- TS-28 The verifier image is actually hardened, not just assumed to be. TS-24 asks you to reason about the attack; this asks you to confirm the defences exist. tests_qc H1 and H3-H5 check the mechanics and warns where it cannot tell whether a defence is needed; you decide whether it is needed here. The reference verifier does four things, and each one closes a specific hole: it installs `util-linux` so the checks can run agent code under `setpriv` as an unprivileged user; it makes `/tests` unreadable to that unprivileged user (`chmod -R go-rwx /tests`) so agent code cannot read the answer key it is being graded against; it removes any pre-existing reward file before grading begins, so an abort cannot leave a stale score standing as the result; and it locks the verifier log directory to root (`chown root:root` plus `chmod 755`) so nothing the agent spawned can write a reward into it. Use 755 rather than 700 there: root ownership is what blocks other writers, and Harbor reads the bind-mounted reward file back as the host user, so a directory it cannot traverse makes that read fail on Linux and errors the trial even though grading succeeded. A bundle that still uses 700 earns an H5 warn, not a fail. Decide by asking one question: does grading execute agent-produced code at all? If it does, all four are load-bearing and a missing one is a fail, so name the hole and the attack it opens. If grading only reads files the agent wrote and never executes them, privilege dropping is not required and the script's H3 warn about `/tests` permissions can be dismissed; say so explicitly rather than leaving it unaddressed. Clearing stale reward files and locking the log directory (H4, H5) matter either way. H1 is outside that judgement entirely, and so is K4. They fire only when grading calls a binary or imports a module the image never installs, which breaks grading whatever the threat model, so both are fails and the reasoning above never excuses them.

## Reference: what the script enforces (context, not a re-check)

tests_qc.py decides these mechanically and owns the verdict on them. They are written out here so you know the shapes your own judgement calls depend on. Do not re-derive them and do not raise a finding from this section. Where the script reports a failure here, confirm it in the file and carry it into your report.

- TS-S1 test_output.py exists, parses as Python, imports `criterion` and `criteria` from `rewardkit`, and no check function name is defined twice. Python silently keeps only the last definition of a duplicated name, so a duplicate means a check the author believes exists never runs. Each check is a top-level function decorated with `@criterion(description=...)` carrying a non-empty description, whose only parameter is `workspace`.
- TS-S2 There are at least 10 checks; more than 35 is bloat worth a warn and a redundancy review.
- TS-S3 Every registration is a module-level `criteria.<name>(weight=W)` call with W an integer literal from {5, 3, 1, -1, -3, -5}. Zero, two, floats, strings, a missing weight and any extra argument are all violations. A `tests/test_weights.json` file is forbidden outright.
- TS-S4 Check functions and registrations map one-to-one in both directions. An unregistered check scores at rewardkit's default weight 1; a registration naming no check of this file pulls in a built-in or crashes the run; a double registration scores the check twice.
- TS-S5 The weights differentiate: all weights being identical means the author never decided what matters most.
- TS-S6 At least one positive and one negative check exist, naming matches sign in both directions (every `negative_*` check carries a negative weight and every negative weight belongs to a `negative_*` check), and the sum of absolute negative weights is at most the sum of positive weights. A naming mismatch silently inverts what the score means; negatives outweighing positives push the floor below -1.
- TS-S7 Nothing under tests/ reads an agent input path (/app/data or any COPY destination of an input directory) unconditionally. Those directories do not exist in the verifier image in separate mode, so an unconditional read is a guaranteed crash at grade time. Reads behind an existence check or an environment switch are safe by design and are not findings.
- TS-S8 test.sh ends with `exec rewardkit /tests --workspace /app --output /logs/verifier/reward.json` and writes no reward bytes itself. The script matches the rewardkit call and reward writes by pattern; read the whole script for any other path that writes or skips (TS-6).
- TS-S9 test.sh contains no skip switches, never sources or executes anything from an agent-writable location, never lets an agent-writable directory shadow PATH, and never consults a pre-existing reward file. Each of these is a direct route for the agent into the grading shell or the score.
- TS-S10 `tests/reward.toml` has the exact shape TS-10 states, and its two weights equal 0.5 divided by the registered positive total of test_output.py and 0.5 divided by the positive criterion total of judge.toml. The script recomputes the weights from the registrations; whether each registration is the weight the check deserves is yours (TS-20).
- TS-S11 tests/Dockerfile exists, has a FROM line, copies the whole tests/ tree to `/tests/`, and installs exactly `harbor-rewardkit==0.2.1`. The harness builds this image with tests/ as the build context and does not upload tests/ at runtime, so an image that never copies the tree greets the verifier with an empty /tests. It also sets `ENV LITELLM_LOCAL_MODEL_COST_MAP=True` (K7): otherwise litellm's GitHub cost-map fetch fails behind the verifier allowlist and rewardkit can deadlock at shutdown before writing reward.json. It also pins litellm with `==` (K8); an unpinned litellm lets the build pick up any release of a package that has already shipped a malicious one. A rebuilt image is the only cure, and Docker's layer cache will reuse a poisoned `pip install` layer forever, so rebuild with `--no-cache` once the line changes.
- TS-S12 Every third-party import in test_output.py other than rewardkit is installed by tests/Dockerfile (mind pip-name aliases such as yaml coming from pyyaml), on Python 3.12 or newer. A missing dependency crashes the verifier at import time. The mkdir for /app is reference convention only; its absence is a warn, the harness creates artifact parent directories itself.
- TS-S13 The oracle is not the verifier's own code wearing a different name. The script measures how much of solve.py reappears in test_output.py and fails at 35%, warning from 20%. Judge the shared block yourself: a small one can still be the entire graded mechanism, and a large one can be an encoder both sides legitimately need. Gate 02 DS-24 carries the full reasoning.
- TS-S14 The verifier image installs every tool the grading scripts invoke, and carries the hardening the threat model requires. Missing tools are always a fail because grading cannot run. The protection warns (restricting /tests, clearing stale reward files, locking the log directory) are warns only because the script cannot tell whether grading executes agent code; you can, so convert them under TS-28.
- TS-S15 The script inspects test_output.py by parsing it, without running it, so it cannot prove a check never raises. A check that can raise on bad agent output is yours (TS-29).
- TS-S16 H6 reads the source for one of three readable-program shapes (the privilege dropper grants read, a grant call names the program, or the verifier executes a file it staged). It cannot follow every indirection, so a pass is evidence and not proof; the owner-only oracle run in Step 10 is what settles TS-30.

Everything else in this gate (semantic determinism, one property per test, negative-check polarity actually verified, instruction/test contradictions, weight distribution judgment, exactness and tolerances, absence-grading positive checks, double payment across any check pair, verifier execution isolation, whether bad agent output can make a check raise) has no script coverage at all: you are the only line of defence there.
