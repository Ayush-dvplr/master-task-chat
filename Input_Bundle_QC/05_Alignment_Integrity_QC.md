## The alignment cross-walk (core of this gate)

Build a table with one row per graded observable (every test, every judged criterion) and one row per instruction promise. Then verify BOTH directions:

- AL-1 Everything graded is promised. The rule differs by layer, because tests and judged criteria relate to the instruction differently. Do not apply one rule to both. TESTS, strict: for each test, point to where the agent could have learned this would matter. Two grounds count and either one is enough. The instruction states it, or the fact is there to be found in the input the agent is handed: any directory under `environment/` that `environment/Dockerfile` copies into the agent image, whatever that directory is called. The prompt does not have to point at the file, because working out the shape of the data you were given is the task; what the fact does have to be is determinate, something the agent can reach from the shipped input by genuine work, as the grounding test below defines it, rather than something the input merely fails to contradict. `tests/` and `solution/` are never grounds, since the agent never sees them. One carve-out, and it is the same one the criteria carry below: where a test grades a rule of engagement rather than a property of the deliverable, what the agent left alone or which paths it touched, discovery does not ground it, because a prohibition cannot be inferred from data. Such a test needs a sentence stating the rule, or the expectation has to be one every competent route would meet anyway, which makes it conduct and moves it to the judged channel (gate 01 IN-15 finds the same defect from the prompt side). What fails is a test asserting a property that is in neither place, which is an oracle expectation that costs the honest agent reward for doing the task correctly. Fail; name the test, the expectation, the files you searched and the two answers the material equally permits, as the grounding test below requires. JUDGED CRITERIA, split by kind (JD-15 covers this inside gate 04; redo it here). The bundle grades two independent things, whether the work came out right and whether the agent stayed inside the rules it was given, so criteria come in three kinds and you classify before you judge. An OUTCOME criterion, which asserts something about what was produced, is a specification item and carries the same burden as a test: point to the instruction sentence, or to the determinate fact in the copied input, or fail it. A CONSTRAINT criterion enforces a rule of engagement the contract states out loud: how the output must be shaped, which files may be touched, which tool must be used, what order the work happens in, what is left alone. A rule of engagement is not the same kind of thing as a fact about the data, and the loose grounding above does not reach it: it must be STATED, in a sentence the agent can read, in the instruction or in any file inside the input directories `environment/Dockerfile` copies into the agent image. No amount of discovery substitutes, because a prohibition cannot be inferred from a CSV. Two exceptions sit on either side of that. A rule about the shape of the output keeps the test burden above, a shipped example included, because a shape is a fact about the artifact rather than a restriction on the agent. And a rule nobody could state without giving away the approach is not a constraint either: demanding its sentence would force the method into the instruction, which gate 01 fails under IN-14, so judge it as conduct. Quote the sentence and name its file. It is graded because it was stated, so compliance is the requirement in itself and you must not ask it to improve the odds of a correct answer. A negative constraint criterion is normal and correct here. What fails is a constraint criterion with no sentence to quote anywhere the agent can read, once you have run it through the conduct steps below and it does not survive them as conduct, because that is an unstated rule costing the honest agent reward (gate 01 IN-15 finds the same defect from the instruction side). A CONDUCT criterion, which judges how the agent worked (derivation method, verification habits, honest reporting, restraint, safety), has no instruction sentence behind it and needs none, because demanding one would force the method into the instruction, which gate 01 fails under IN-14. The two steps below exist precisely because nobody told the agent, so they apply here and never to a constraint criterion. Step 1: would every competent route to a correct end state satisfy this criterion? If yes it is legitimate, because it constrains nothing. If no, step 2: does the approach it requires make a correct end state more likely, or is it just a preference? A preference, where two solutions differing only on this point are equally good, must be removed; an odds-raising approach earns its place. A negative CONDUCT criterion penalising a legitimate approach is always a fail (negatives aimed at cheating or misconduct, gate 04 JD-11, are not approaches). A preference weighted 5 is a fail and weighted 1 or 3 is a minor; an odds-raising approach weighted 5 is a minor. Then name the requirement the conduct SERVES, not one that states it. A conduct criterion serving no requirement at all is off-topic and fails. Quote the criterion and say which step it broke.
  The grounding test. This is the one definition of "grounded" for the whole QC bundle. Gate 01 IN-8, IN-16 and IN-17, gate 02 DS-21 and DS-25, gate 03 TS-17, TS-18 and TS-19, gate 04 JD-15 and JD-16, client checks CL-5 and CL-10, F0e and Step 11 of the final checklist all decide grounding with it and with no reading of their own, and a fact that passes it is what this bundle calls determinate. Grounded answers one question only, whether the agent COULD have known. It does not say the item is worth grading: an answer sitting in the data ready to lift passes this test and still fails CL-3, and one reachable only through material the image should never have exposed passes it and still fails DS-26.

  What it asks. A graded item is grounded when an agent doing the task honestly could have arrived at what the item demands from the material it was given. The question is never "does a sentence say this". The question is "is there a route from the material to this fact". The material is the instruction plus every file inside the input directories `environment/Dockerfile` copies into the agent image, whether read, parsed, computed over, run, or combined with each other, together with whatever the running agent image itself exposes: the tools `environment/Dockerfile` installs, the variables it sets, the files its build steps create. `tests/` and `solution/` are never material, because the agent never sees them, and neither is a file under `environment/` that the Dockerfile never copies in.

  What grounds a fact. The fact does not have to be written anywhere, either whole or in part, and no check needs a sentence of its own. Any one of these is enough:
  - a sentence stating it, in the instruction or in any material file, in any wording, including a paraphrase that never uses the word the check uses;
  - a value present in the data;
  - a value computed from the data, by a rule a material file states or by ordinary arithmetic on what ships;
  - a convention the material exhibits throughout for the same kind of value the output carries, with no exception anywhere, so that any other choice would break a pattern the agent can see (every date in every input is ISO 8601, so ISO 8601 dates in the output are grounded); a convention governs only its own kind of value, so input rows sorted by id do not establish that output rows are sorted, and an ordering, spelling or layout the output must follow needs its own ground;
  - a behaviour observed by running a tool, binary or program that ships;
  - a consequence of two or more of these together, the commonest being a stated rule applied to shipped data.

  What does not ground a fact. The material being silent, so that the graded answer is one of several the material allows equally well. A fact visible only in `tests/` or `solution/`. A convention the reviewer thinks is usual when nothing in the material exhibits it.

  How to run it. Apply these four steps, in this order, to each test and each outcome criterion, and stop at the first step that settles it.
  1. Name the fact. Write the single fact the check needs the agent to have known, as one sentence. Not the check's name, not its purpose: the fact ("an empty timestamp means the record is unreadable", "region totals are summed over net amounts"). If you cannot write it, there is no finding, and most proposed grounding findings end here.
  2. Look for it stated. Is it fixed by a sentence anywhere in the material, in any wording, whole or in pieces? The sentence need not mention the check, the output file, or the test's vocabulary. If yes, it is grounded; stop.
  3. Look for a route to it. Could an honest agent reach it by reading, parsing, computing, running what ships, or following a convention the data shows? Write the route as one line: which file, which operation, what result ("records.csv, read the timestamp column, 3 of 40 rows are empty"). If you can write that line, it is grounded; stop. Difficulty does not matter: a long, unobvious or many-step route grounds the fact exactly as a one-step route does, because working it out is the task. What does matter is that every step is forced by the material. A path that is one of several the material equally allows is a guess rather than a route, however few of the choices lead to the graded answer, and it grounds nothing: hard and forced passes, lucky fails. A step is also forced when the material lets the agent check each candidate and tell the right one apart, a round-trip that only succeeds on the true answer, a checksum that only matches it, a shipped example output to compare against. Searching a thousand candidates that way is long grinding search, which DS-21 protects; what fails is a choice nothing in the material can confirm. When you find a guess, the fix is to make the material settle it (an example, a fixture, something the agent can check against), compare in a way that accepts every permitted answer, or stop grading it; stating it in the prompt is only one option, and never the required one.
  4. Only if steps 2 and 3 both failed, decide what kind of failure it is. If the fact is a rule of engagement (a prohibition, a scope limit, which files may be touched, an order the work itself must follow), steps 2 and 3 never applied to it, since no data exhibits a prohibition: it needs a stated sentence under the constraint branch above, or it is conduct. Otherwise the check is ungrounded, and that is the fail.

  What a grounding finding must contain. A grounding finding claims that no route exists, so it must show the search, and the burden sits with you, not with the author. It must give: the fact from step 1; every material file you searched; and at least two answers the material permits equally well, the graded one among them, because if you cannot name a second permitted answer the material has settled the question and the check is grounded. A second answer counts only when the material supports it as well as the graded one, not merely when some file mentions it: where the bundle plants a stale or wrong value and something the agent can read marks the authority (CL-6), that value is a trap the agent was meant to see through, not a second permitted answer. "The instruction does not mention X" is never a finding. "Nothing states X" is never a finding. A finding missing any of the three parts is incomplete and must be withdrawn. When in doubt, it passes, except against a client check: a pass here never clears a CL check, which you still run on its own terms (Final_checklist.md, "Client feedback checks").

  Worked cases. Measure against these.

| what the check needs | what the shipped input holds | grounded |

| region totals are sums of net amounts | orders.csv carries gross and net per row, and rules.md says "revenue is always reported net" | yes, step 3: a stated rule applied to the data, though no sentence mentions region totals |

  The rounding row is the one to carry forward: one file can settle one demand and leave the next one open, so judge the fact the check actually needs rather than the file it came from.
- AL-2 Everything promised is graded. Enumerate from `instruction.md` alone. The unit here is what the PROMPT promises, not everything any shipped file happens to say, so a spec that documents more than this task asks for does not turn its spare detail into ungraded promises. Where the prompt delegates instead of restating ("your output must conform to `schema.json`"), follow the pointer and enumerate the delegated rules the delegation actually invokes, not the whole file: otherwise one sentence collapses a forty-field schema into a single row, and one test touching one field looks like full coverage. A set the delegation invokes uniformly is one promise, not one promise per member: where a single sentence binds forty key spellings, the promise is that the output conforms, and one check whose comparison spans all forty covers it, so ask whether the comparison really reaches the whole set rather than asking for a check per field. Enumerate a member on its own only where the prompt singles it out, or where it carries its own branch or edge case. For each requirement so enumerated, point to the test or the judged criterion that checks it; either channel satisfies this. An ungraded promise invites solutions that skip it. Strict fail; name the requirement and state that no test or criterion covers it.
- AL-3 Exact-shape agreement: output formats, error-object shapes, key names, exit codes, file paths, precedence orders. The classic bug: instruction demands {"error": "x", "version": N} while the test asserts the object equals {"error": "x"}. Compare every literal shape the agent can see against every shape anything grades, byte by byte. "Can see" means the instruction and anything shipped in the input directories environment/Dockerfile copies into the agent image, whether or not the prompt names them; read those files as part of the contract, because for most bundles the exact shapes live there rather than in the prompt. "Anything grades" means the tests AND any judged criterion that names a shape, since a criterion demanding one format while the contract states another traps the agent exactly as a test would. Any mismatch where following the contract loses reward is an automatic fail, and a shape that contradicts between the instruction and a shipped spec file is the same fail.
- AL-4 Hidden behaviours: a behaviour of the DELIVERABLE that the tests or an outcome judged criterion grades while the contract forbids or omits it, where the contract is the instruction together with whatever the copied input establishes (AL-1) (extra error strings when the contract says "do not invent new error strings", undocumented edge cases carrying graded weight in either layer). Fail. A solution handling more than the contract mentions is not this finding on its own: a reference implementation may be as robust as its author likes, and the defect exists only where something grades the extra behaviour. Conduct criteria are NOT hidden behaviours and never belong in this finding: JD-15 exempts them from needing a sentence anywhere, so a criterion about verification habits or honest reporting being absent from the contract is correct by design, not a defect.
- AL-5 The oracle passes its own tests: trace solve.sh output through every test. Any test the oracle would fail proves the bundle broken. Fail.
- AL-6 The judged criteria agree with the solution and the instruction (JD-7/JD-10 deep pass): re-verify the three most load-bearing criteria yourself.
- AL-27 Trigger depth: a rule only counts as graded when the test's input actually constructs the situation where the rule matters. A test can be named after a rule, tick the AL-2 mapping on paper, and still never exercise it because no fixture creates the triggering case. The classic shape is an ordering or precedence rule ("check the magic before the version"): unless some graded input carries BOTH faults at once, the order never matters and a solver checking things backwards still scores full reward. For every ordering, precedence, or tie-break rule the bundle grades, whether the instruction states it or the copied input establishes it (AL-1), trace the fixtures: for each adjacent pair in the chain, find the graded input with both conditions present and the assertion that the earlier one wins. For every other rule, ask "which graded input would come out differently if the solver broke exactly this rule?" - no such input means the rule is ungraded regardless of what the test is called. Scope this to rules the bundle actually grades or the prompt actually promises. A rule a shipped spec documents while nothing grades it and no graded input triggers it is inert rather than ungraded: the contract describes a general system and this corpus exercises part of it, which is the same spare detail AL-2 declines to count as a promise, and a solver scoring full marks while ignoring that rule is scoring correctly, because the rule never applied to the data it was given. The fail is for a rule something claims to grade, a check named after it or a criterion asserting it, where no fixture constructs the triggering case, because then the check is decoration and the reward cannot see the rule at all. Where the prompt itself singles out a rule no graded input triggers, report that the data does not support what the prompt emphasises rather than that the rule is ungraded. Fail; name the rule, the check that claims it, and the missing fixture.
- AL-28 No penalty stacking. For every negative check in test_output.py AND every negative-weight criterion in judge.toml, name the single concrete agent action that triggers it (hardcoded the shipped answers; edited a file outside the allowed scope; read tests/; emitted nondeterministic output...). Group the negatives by triggering action, ACROSS both layers. One mistake must cost at most one maximum-severity penalty. In the tests, sum the absolute weights in each group: a combined penalty above 5 is stacked, the agent punished twice or three times for one decision and the reward floor distorted for everyone. In `tests/judge.toml`, stacking is two negative-weight criteria pricing one act (sum of absolute weights above 5). Across layers it is one act subtracting in the tests and again in a negative-weight criterion. Example shape: the same hardcoding act firing a -5 check and a -3 check costs 8 for one decision, and the same act firing a -5 judged criterion subtracts a third time in the other channel. Fix: keep the strictest single penalty and retarget or drop the rest, or carve the triggers into genuinely non-overlapping conditions so no single action fires more than one. Fail; show the group, its members, and what each one costs.

## Anti-cheat audit (adversarial pass)

Think like an agent whose only goal is reward. For each vector, state whether it works and why not:

- AL-10 Hardcode shipped answers: if data contains labelled examples, could an agent score above the honest floor by memorizing them? The negative tests must catch exactly this.
- AL-11 Grade-time environment abuse: tests reading anything agent-writable (input-path reads such as /app/data crash - Gate 03; but also /tmp state, env vars, marker files an agent could plant).
- AL-12 Grader influence: could the agent's artifacts shadow a tool, monkey-patch a module, or pre-write a file the verifier trusts? Remember artifacts land at their exact declared absolute paths in the verifier container - check that neither test.sh nor any check in test_output.py executes or imports anything from agent-written paths except deliberately running the declared artifacts as subprocesses.
- AL-13 Answer-in-reach: could the agent reconstruct expected outputs from data plus instruction without doing the work (weak redaction, derivable keys, answers encoded in filenames/sizes/comments)?
- AL-14 Reward-file tampering: instruction never mentions reward paths (Gate 01); test.sh clears stale reward files, locks `/logs/verifier`, writes no reward itself and ends with `exec rewardkit` (Gate 03 TS-6); no check can raise on agent output and leave the run without a reward (TS-29); no agent subprocess outlives its check to rewrite `reward.json` (TS-24); and `tests/reward.toml` still matches both channels' positive totals (TS-10). Re-confirm the combination end to end.
- AL-15 Offline contract consistency: every layer must agree that the task runs with no network. `[environment] network_mode` is pinned to `"no-network"` for every task, so there is no per-task policy to look up - the comparison is between the layers and that fixed fact, not between the layers and a value. Nothing may assume network at solve time or grade time: an instruction that tells the agent to download, a Dockerfile that fetches at run time rather than build time, a solution that installs what it needs, or a test that reaches an endpoint are each a fail. The `[verifier]` and `[agent]` network lines are NOT part of this comparison: the judge needs egress to score the judged channel and the agent harness needs egress to reach its own model, neither of which is the task being online. An offline task with an online verifier and an online agent harness is the normal combination rather than a contradiction. Do not raise a finding merely because the bundle never mentions the network; silence is the expected state. If the work genuinely requires an outside endpoint, say so here as a design finding against the offline contract.
- AL-24 Filename-keyed behaviour: could a "solution" skip the real work by keying on input filenames instead of content (a lookup table from names to memorized answers; rename the file and it breaks)? If the data layout makes this profitable, something in the tests must defeat it (e.g. eval inputs the agent never saw, content-based checks).
- AL-25 Nondeterministic output: could an agent that guesses, races, or emits different output on each run luck into reward? Grading must be robust to this (enough independent inputs that guessing cannot win, or repeated-run identity where the instruction promises determinism).
- AL-26 Metadata truthfulness: read instruction.md, decide for yourself what kind of work DOMINATES the task, then compare against the declared metadata. `[metadata] category` must name that dominant kind of work: a mismatch is a fail, and it is still a fail when the declared category appears only as a side aspect of the task (a Debugging task with a security flavour declared as "Security" fails). `[task] description` must be an honest summary of what the instruction asks: misleading = fail, sloppy but true = minor. `keywords` and `tags` must relate to the task's actual subject matter: completely unrelated entries are a fail, weak-but-related entries are a warn.

## Task security (malicious-code audit)

Review every file in the bundle - both Dockerfiles, test.sh, solve.sh, solve.py, test_output.py, and every file under environment/ - as hostile until proven clean. The verifier and the agent both run as root, and reviewers run bundles on their own machines, so all bundle files are trust surface.

- AL-19 No credential or secret exfiltration: no credential shipped anywhere (including a literal value in `[verifier.env]`). Apart from the pinned `OPENAI_API_KEY` placeholder, nothing reads environment variables for credentials, ~/.ssh, ~/.aws, or any credential store, and nothing transmits or stages such values. Fail.
- AL-20 No network exfiltration or supply-chain risk: no curl/wget piped to a shell, no downloading and executing code from URLs, nothing that transmits bundle contents or grading data outward. The task runs offline, so there must be no outbound calls at all in the instruction, the Dockerfile's runtime path, the solution or the tests; AL-15 owns the plain "this cannot work offline" case, while what stays a fail here, and would stay one under any policy, is malicious use: exfiltration of secrets, bundle contents or grading data, and downloading then executing code. Fail. One exception: the official uv installer piped to a shell at build time in `environment/Dockerfile`, exactly `curl -LsSf https://astral.sh/uv/install.sh | sh`, as in the recommended DS-29 block. Any other piped download, or this one anywhere else (tests/Dockerfile, solve.sh, test.sh, the checks), still fails.
- AL-21 No destructive or resource-abuse operations: no rm -rf outside the task's own working tree, no fork bombs, no disk-filling loops, no background daemons (a service a check starts for measurement and stops before the check returns is fine). Fail.
- AL-22 No obfuscated payloads: no base64/hex-encoded commands that get decoded and executed, no eval/exec of dynamically constructed strings, no invisible or deceptive Unicode. Encoding that is the task's own problem domain is fine when the instruction or TRUTH.md explains it. Fail.
- AL-23 No prompt injection in agent-visible files: nothing under environment/ or in instruction.md contains text that tries to steer the agent outside the task ("ignore previous instructions", instructions addressed to the model, hidden directives in comments or metadata). Fail.
