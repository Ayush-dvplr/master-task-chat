## Root cause

The release train compiler walks the ledger in record sequence order (`seq`) while the authority orders by `effective_generation,seq`. Wherever a lower generation was recorded after a higher one for the same scope (records 17/18, 19/20, 22/43, 48/49), the compiler keeps the later recorded value, and record 52's invite_decline value is likewise ordering dependent, so the generated export snapshot, and the index, runtime and gate report built from it, carry five wrong urgency ranks. The compiler uses the same journal view as the authority, so the control replay reproduces the snapshot digest exactly, which falsifies `journal_backlog` and points at `compiler_ordering_key`.

## Pitfalls

- Letting the last `apply_change` status win for record 17.
- Following the last supersede in the file even when it is rejected (`sc-11-4`, `sc-12-4`).
- Measuring the timer_pause window from the oldest open deprecation or from the one the restore closed, or using `>` at the window boundary (`focus_hold`).
- Reading a written lineage anchor literally after a live supersede of its scope retired it (record 19).
- Applying a revise that writes the value already current, or deciding that once for both orderings (records 51, 52).
- Taking the generation from effective records only (record 46 is inert).
- Copying the snapshot's name ordered retired list or its stamped version 9.2.1.
- Giving record 29 `revise_names_inactive_scope` instead of `rolled_back`.
- Hardcoding A2's recovery rule instead of reading the addenda, so a republished window is ignored.
- Ordering window retirements that share a deprecation generation by anything other than the scope name.
- Trusting the gate report, which compares the snapshot with its own descendant.
