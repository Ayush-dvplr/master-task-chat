The Coredrop capture agent ships crash dumps in MDUMP, a proprietary binary container, and the postmortem pipeline has been mis-reading them. The pipeline still decodes with `/app/data/MDUMP-legacy-decoder.py`, which was written against an old revision of the format and has never been brought up to date; triage has traced several mis-read crash dumps back to it. Treat that file as a suspect, not a reference. The format is written down under `/app/data`, with the container format specification as the authority, plus an error-code reference, an encoder note, a primer, a glossary, byte-level worked examples, the capture team's field notes on three newer agent build lines (with hand-verified decodings for one, decoder fingerprints for another, and a normative transition note for the newest), and a log of 16,000 field captures pulled from the collector. Some field notes do not give their builds' rules in full, so that part has to be recovered from the data, and the codec has to handle every documented build line, not only the one the specification covers. Part of the job is working out which file answers which question. Leave everything under `/app/data` as it is.

Replace the legacy tool with a correct codec. Write the decoder to `/app/decode.py` and the encoder to `/app/encode.py`. `python3 /app/decode.py <capture>` must print exactly one JSON object on stdout and exit 0: the decoded document when the capture is valid, or the single error object the error-code reference defines when it is not, chosen by the precedence the specification sets out. Triage uses these outputs to find damage by position, so every decoded record gives its byte offset in the body and every error inside the body gives the offset of the field that failed, counted the way the specification and the error-code reference define them. It must still exit 0 on damaged or truncated input. `python3 /app/encode.py <document.json> <capture>` must read a document in the decoder's shape and write the capture it came from, byte for byte. A document whose stored values or offsets do not match its own records has been edited by hand, and the encoder must refuse it the way the encoder note describes instead of writing a capture. Both programs run in a clean Python 3.12 with only the standard library, and they cannot import helper modules you write next to them or read anything under `/app/data` while they run.

Also leave four reports, in the shapes the decoder appendix lays out: `/app/out/decoded_examples.jsonl` (captures you build yourself and their decodings), `/app/out/format_report.json` (the grammar you recovered, tallies for your examples and for the whole capture log, and a per-capture status and fingerprint for every logged capture), `/app/out/roundtrip_report.json` (proof that each of your examples survives `encode(decode(bytes)) == bytes`), and `/app/out/error_analysis.json` (the error precedence, your decoder's output on deliberately damaged copies of your first example, and the error tally over the capture log). Each must come out byte-identical on a second run.

Your decoder and encoder will be run on fresh captures and documents you have not seen, valid, damaged in every way the specification describes, or edited by hand, and an output counts only when every key and value in it is exactly right. Output that depends on the input filename, changes between two runs on the same input, or reassigns the standard-library functions it uses counts against you. MDUMP is invented for this task, so there is nothing about it to find elsewhere.

You have 14400 seconds to complete this task. Do not cheat by using online solutions or hints specific to this task.
