# Service contract: reservation quota settlement

This contract governs the settlement run of the inference serving platform for one settlement period. The period has five traffic classes, always taken in this class order: visible, peak, steady, burst, latency. A class is in scope when the extract holds a request log for it; a class with no request log is out of scope.

Control file: the control file (ctl_r7.json) holds the label of the period (label), the correction cutoff (cutoff_seq), the review threshold of recommendations (review_shift_ru), the window of every class (windows, each a list of the start instant and the end instant), and, under files, the names of the register database (register), the group crosswalk (crosswalk), the pool profiles (profiles), the rate card (rates), the model weight table (weights), the meter sheet (units), the two correction layers (amendments, overrides) and the prior output (prior). The windows key maps each class name to its window. The request logs are the files of the extract whose names start with ev_ and end with .rqb, each an RQB1 container as lg_rqb.md defines it. File names in the control file are relative to the folder of the control file.

Authority: the register, which is the register database (tn_reg.sqlite) together with the group crosswalk and the pool profiles the control file names, is the authority for tenants, pools and aliases. Plain-text copies of register tables are backups taken at an earlier time, and nothing in a settlement run is read from them. The method constants of the service (the model weights and the rates) are kept only in the binary documents the control file names, never in a plain-text file; the units per RU are written nowhere and come from the meter sheet.

File formats: the rate card, the model weight table and the pool profiles are Office Open XML files as ECMA-376 defines them. A document is read as a consumer that understands every namespace ECMA-376 defines and no other. The meter sheet is a PDF file as ISO 32000-1 (PDF 1.7) defines it. The register is a SQLite 3 database. The comma and tab separated sheets are delimited text as RFC 4180 defines it, with the stated delimiter in place of the comma, and the first row of each names its columns.

Register: the table tenant has the columns code, traffic_class, pool, contracted_ru and retired (1 for retired, 0 otherwise), one row per tenant and class. The table pool has the columns pool_id, traffic_class and grp, one row per pool; pool ids are unique across all classes. The parameters of a pool are not in the database: the group crosswalk (xw_05.csv, comma separated, columns grp and prof_code) maps the group of a pool to a profile code, and the pool profiles (the document pp_31.docx, whose one table has the columns prof_code, start_step, patience and budget) give the starting step, patience and budget of each profile code as whole numbers of at least one. The profiles may hold codes that no group maps to. The pool table of the documents means the pool rows of the database with these parameters joined on. The table alias has the columns api_key, tenant and eff_from (an instant written as in st_demand.md).

Corrections: two correction layers change register fields of a tenant row, the amendments (am_07.tsv, tab separated, columns seq, tenant, traffic_class, field, value) and the overrides (ov_07.jsonl, one JSON object per line with the same keys). The field is one of contracted_ru (a whole number), pool (a pool id) and retired (yes or no). The register gives the base value of every field. Amendments apply over it in increasing seq, a later amendment of a field replacing an earlier one. Overrides apply over the amendments: an override of a field replaces every amendment of that field, whatever their seq, and an override with a higher seq replaces one with a lower seq. No two correction entries share a seq. A correction whose seq is greater than the correction cutoff does not apply, in either layer. A correction naming a tenant and class with no register row does nothing. Each correction entry has one status: cutoff when its seq is greater than the cutoff (whatever it names), unmatched when its seq is within the cutoff and it names no register row, and applied otherwise.

Prior output: the prior output file holds the settled reservations of an earlier settlement run of this period. It was produced by a superseded build, its figures are untrusted, and it is used only for the comparison report of fm_reports.md.

Invariants: every request log is well formed as lg_rqb.md defines it, its checksum included; every req_id is unique within its request log, and a req_id found in two request logs of one class names the same request in both, every field alike; every request log holds at least one request and names one traffic class only; the register holds one tenant row per tenant and class; every pool a tenant row names, after corrections, is a pool of the pool table with the class of that row; every group of the pool table appears exactly once in the crosswalk; every profile code appears at most once in the profiles and every code the crosswalk names appears there; every class in scope has a rate row in force at its window end; every model a request log names is in the model weight table; no two alias rows share a key and an effective instant; every status is ok, cut or rejected; the meter readings settle the units per RU of every pool that needs one, so an extract whose readings no assignment of admissible values meets, or more than one assignment meets, breaks this invariant. An extract that breaks any of these is rejected as a whole.

Extracts this contract covers hold up to 20 pools, a meter sheet of up to 40 readings and up to 6 api keys in a reading; up to 11 pools of an extract may appear only in readings that also name another pool.

Terms defined in the glossary (gl_00.md) carry their defined meaning wherever they appear in the documents. Stage dependencies are listed in od_stage.md, the boundary cases in ed_cases.md, the rounding in pr_num.md, and the report forms in fm_reports.md.
