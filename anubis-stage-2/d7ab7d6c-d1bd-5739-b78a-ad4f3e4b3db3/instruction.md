Our game hosting crew lost the tool that replays its arena slot request journal into a session table, and the source went with it. Everything left of it is in `/app/data`. `conventions.md` holds the rules the team wrote down, `reports.md` gives the exact shape of the three output files, and `handover.md` holds notes the last arena operator wrote from memory. The team does not trust `handover.md`; where it disagrees with `conventions.md` or the worked examples, it is wrong. Read all three notes before you start writing code.

Four worked examples ship with their answers. Their input files carry the prefix `example_a_`, `example_b_`, `example_c_` or `example_d_`, and the files they should produce carry the same prefix followed by `out_`, such as `example_c_out_sessions.json`. The five input files with no prefix (`requests.jsonl`, `servers.json`, `owned.csv`, `sessions.prev.json`, `manifest.json`) are the live intake, and nobody has its answers.

`conventions.md` says that six rules of the old tool were never written down. Working out those six rules from the worked examples is part of the task. They cover the order in which servers are scanned, whether a session is still live at the second its `until` arrives, which of several `owned.csv` rows for one player stands, what happens to a server right after its session is released, whether a returning player is offered a server they played on before, and the order of records that share one second.

Worked examples `example_a_` and `example_b_` use mode word zero. `example_c_` uses mode word 170 and `example_d_` uses mode word 84, so each of the seven bits is set in exactly one worked example. The live intake has no answers, but its manifest carries a SHA-256 for each report and for each of the two tables in `sessions.json`.

Write the replay tool as one Python program at `/app/out/arena.py`, run as `python3 /app/out/arena.py IN_DIR OUT_DIR`.
