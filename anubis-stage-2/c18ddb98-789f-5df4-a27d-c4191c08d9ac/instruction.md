A change data capture platform has finished collecting one ingest window and now has to close it. Change records from a set of upstream feeds landed in a staging area during the window, and the platform owes its operators a settled account of that window: which records it kept, which it let go and why, which feeds it stopped trusting, what the window cost, how that cost splits across the parts of the estate, and a proof that nothing was lost or invented along the way. Your job is to produce that settled account.

You have 7200 seconds to complete this task.

Everything you need is under `/app/data`. There you will find the machine readable registers the platform keeps, a reference set of rulebooks written for the humans who run it, a statement of the invariants every settled window has to satisfy, a calibration slice with the figures a small window already settled to, and one complete artifact the platform produced for that small window. Read all of it before you write anything. The rulebooks are filed the way a reference set is filed, grouped by subsystem and shelved alphabetically, which is not the order in which the rules bear on a record. Working out the order in which they bear on a record is part of the job, and the calibration figures are what settle it.

Five properties of this platform have to be recovered rather than read off. They are the sequence in which the four rate adjustments compose, the backpressure coefficient the surcharge is a share of, the spacing of the settlement grid, the convention the platform uses for a value that falls between two grid points, and the reading of the tombstone rule. The last of those is stated plainly in the rulebooks, and is listed here because the calibration figures confirm it independently and because reading it the ordinary way rather than the way the platform states it will change a great deal. Exactly one combination of those five reproduces every figure published for the calibration slice. Find it, use it, and report it.

Write everything into `/app/out`, and do not modify anything under `/app/data`.

Deliver a program at `/app/out/settle_ingest.py`. It takes two positional arguments, a directory of registers and a directory to write into, and it settles whatever window it is given. It must run on Python 3.12 with nothing but the standard library, must finish a window this size well inside 300 seconds, and must contain no value that is true only of this particular window. Anything it needs about the platform it has to recover from the registers it was pointed at, because it will be run against other windows. A register directory holds the machine readable registers and the calibration material and nothing else: the rulebooks, the invariant statement and the example artifact are written for you rather than for the program, so do not expect them beside the registers it is handed. Those registers state their rows in no fixed order, and every figure the platform parameterises itself with sits in one of them, so the settled account a register directory produces has to be a function of what its rows say and never of the order they arrive in or of what this window happened to publish. The program will be handed windows whose calendars, policies, cards, incidents, exceptions, caps, allowances and payloads all differ from these, including windows that curate nothing at all, and it has to close each of them.

Running that program against `/app/data` has to produce the settled window. `/app/out/summary.json` is the account of the window as a whole, and it carries an object named `resolved_parameters` holding the five properties you recovered, under the key names and with the legal values the calibration material sets out. `/app/out/reconciliation.json` carries the conservation identities and their residuals. `/app/out/ingest_audit.json` carries the record by record ledger and the identity work behind it. `/app/out/data_quality.json` carries what the window noticed about its own inputs. `/app/out/slot_designation.json` carries the reserve slots the window held back.

Alongside those, write one report for every domain that is in scope for this window and one for every channel that is in scope, into the same directory, named as the partition rulebook says partition reports are named. The registers this window ships admit eight candidate partition reports, and the naming rule puts them at `/app/out/domain_ledgerworks.json`, `/app/out/domain_meridian.json`, `/app/out/domain_northfield.json`, `/app/out/domain_oakline.json`, `/app/out/domain_penumbra.json`, `/app/out/domain_quarryside.json`, `/app/out/channel_cascade.json` and `/app/out/channel_tidewater.json`. Which of those eight are in scope is a consequence of how the window settles, so the set you write is a result rather than a given, and it is published nowhere. Do not assume it, derive it. Leave every candidate that settles out of scope uncreated: a report that should not exist is as wrong as one that is missing.

This window has two outcomes of equal standing, and it is closed only when both are right. The first is the settled account above. The second is the egress layer the reference set carries in a rulebook filed under E, which reads the curated ledger the settlement produced and settles it onto a per octet basis. It is not an appendix to the settlement and it is not optional: it carries its own six artifacts, its own rules and its own conventions, and a correct settlement with a wrong egress layer is an unclosed window in exactly the way a wrong settlement is. Run it second because it consumes the curated ledger, not because it matters less.

The egress layer turns each curated record into what it cost per octet of payload it carried, holds back the records that burst, and settles the rest into a pool, an apportionment of the window's curated payload units and a digest. Write the egress account to `/app/out/egress_summary.json`, the per-record rates to `/app/out/egress_rates.json`, the records it held back to `/app/out/egress_bursts.json`, the ranked order the digest is taken over to `/app/out/egress_order.json`, the payload apportionment to `/app/out/egress_apportionment.json`, and the per-group rendering to `/app/out/egress_ladder.csv`. The artifact schema fixes the key names, the row shapes and the CSV header of all six; emit the figures under the names it states.

The egress rulebook does not reuse the conventions of the rulebooks above it. Its one division truncates where every other division in the reference set places its result on the settlement grid, its rejection rule names the estimator it uses and the sample size it never rejects from, its medians settle an even sample without averaging and without placing the result, and the order it emits records in is not the canonical ledger order. Its rejection threshold is crossed only by a record that stands strictly above it, so a record sitting exactly on the threshold is retained rather than held back. Take each of those from that rulebook rather than from the ones it sits on top of. Its sigma, its modulus and its octets per payload unit are published in a register of their own.

The artifact the platform produced for the calibration slice is the authority on the form every artifact takes, down to the byte. No prose anywhere describes that form. Match the example.

When you are done, tell me in your final message the charge the window settled, how many records it curated, how many it withdrew and how many it quarantined, the payload units it curated, the feeds it designated as reserve slots, the feeds it quarantined, the domains and channels that ended up in scope, and each of the five recovered properties quoted exactly as you wrote them into the summary. Say what the conservation residuals came to.

Report the egress layer in that same message: the egress pool and the egress digest you settled, the count of curated records the burst rule retained and the count it held back, each record it held back together with the median, the deviation and the threshold that decided it, and the payload share each group took with a confirmation that the shares sum to the curated payload units. Show the per octet arithmetic for one record the rule retained and one it held back.

Everything graded here has to come from what is under `/app/data`. No outside source has this platform or this window in it.
