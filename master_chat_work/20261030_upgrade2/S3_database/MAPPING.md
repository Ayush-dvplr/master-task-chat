## Migration ordering and validation

1. Freeze a *read-only snapshot* by copying source bytes into a migration staging folder while the master pauses its own writes. The harness and workers may continue, but mark their snapshot cutoff and replay new inbox/event records later. Hash every source. A file that changes during the copy is retried; no source is edited.
2. Import pending, tasks, board, levers, then scores, QC results, decisions, feedback, lessons, auto and queue snapshots, and historical records into a **new** DB. FK failures, duplicate keys, malformed JSON, and source drift are listed before any cutover. Stage/history records inferred from a current snapshot are labelled as such.
3. Dry run `PRAGMA foreign_key_check; PRAGMA integrity_check;` and compare counts: tasks 34, sessions 352, pending items 457/history 1,249, decisions 589, feedback 26, lessons 88, levers 68, ideas 5, peer tasks 20, auto state 10, auto events 308 plus night 43, queue runs 92, QC results 86. Scores must account for all 112 raw lines even if fewer become typed `runs`. Recompute counts at cutover; these are example baseline values, not fixed assertions.
4. Compare current `status.py` output, pending list, `BOARD.md`, latest valid score per task, and QC round counts to DB-generated views. Manually resolve the one observed board-result SHA mismatch and all orphan QC results before declaring equivalence.
5. Switch read paths first. Keep old files intact as rollback and archive inputs. Switch master writes only after a shadow period with zero count/view differences. Generate `BOARD.md` and a compact `STATUS.md` from one DB snapshot; keep `status.py` as a CLI facade. Human-readable views remain generated artifacts, not competing truth.

## Safety and rollback

One master process owns all DB writes. Use SQLite WAL, `busy_timeout=5000`, `foreign_keys=ON`, one short `BEGIN IMMEDIATE` transaction per merge, and `synchronous=FULL` for the authoritative DB. Readers use `mode=ro` and never create tables. Use SQLite's backup API (WAL-consistent snapshot) before migration/cutover, before schema upgrades, and once daily after the final merge; store under `master_chat_tasks/backups/` with timestamp and SHA manifest, keep 14 daily and 4 weekly copies. Verify each with `quick_check` and an open/restore rehearsal. Do not copy only the `.sqlite` file while WAL is active. On failed migration, delete only the new staging DB and continue on existing files. On failed cutover, stop DB writes, restore the last verified backup to a new path, replay retained inboxes by SHA, compare counts/views, and point the master back to the old file workflow until differences are resolved. No rollback deletes worker inbox or original result files.
