## 3. Inbox protocol and conflict behavior

**Finding.** Current `intake.py session` reads a board path, checks `result*.json` parse, and optionally changes board and pending (`tools/intake.py:80-109`); it does not have a shared worker inbox or an atomic board/pending update. Worker result schemas already contain the board SHA in standard templates, but older/research outputs may omit a slug or step (`scripts/results_inventory.py` field counts). `INBOX_SPEC.md` defines a top-level superset of the result object with version, board base, result/artifact hashes, and proposed changes.

**Recommendation.** Each worker writes `master_chat_tasks/inbox/<sha>.json` through a unique temp file, fsync, and rename. Only the master reads it and, after Ayush's exact `done: <sha>`, validates exact board identity, paths, hashes, tree/score evidence, and status; then it commits result, typed rows, board status, and pending history in one transaction. Same SHA + same file hash is idempotent. A changed hash, unknown SHA, changed board/result path, or incompatible stage is refused and recorded as a conflict; inbox remains untouched. Auto mode can report readiness but cannot merge without Ayush's `done`, following U15 (`REQUEST.md`, sections A/E). Expected gain: workers never race on the DB and every merge has a reproducible source file. Risk: strict validation may reject older result variants; verify with a corpus of actual P2/P9/P11/P12/P13/P16/P17 and research results, including blocked/partial cases, before requiring the inbox for all new sessions.

## 4. SQLite safety, backup, migration, rollback

**Finding.** `python3 scripts/test_schema.py` created a disposable on-disk DB in OUT, loaded `schema.sql`, and returned `journal_mode wal`, `synchronous 2` (FULL), `busy_timeout 5000`, `integrity_check ok`, `foreign_key_check 0`, and 25 tables. This tests DDL/settings only, not migration or live concurrency. Existing `pending.db` is live and was inspected only with `sqlite3 'file:.../pending.db?mode=ro'` or Python URI read-only connections (`scripts/inventory.py`, `scripts/cost_baseline.py`). The queue file already has a separate operational owner and lock (`scripts/master_queue.py:148-164`).

**Recommendation.** For the on-disk authoritative DB use WAL, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=FULL`, one master writer, and short transactions. Back up with SQLite's backup API before migration/cutover, before schema upgrades, and daily after final merge; retain 14 daily and 4 weekly verified copies in `master_chat_tasks/backups/`. Use a read-only source snapshot, dry-run import, `foreign_key_check`, `integrity_check`, row-count comparison, and view comparison before cutover (`MAPPING.md`). On failure, keep old files authoritative; after cutover, restore a verified DB backup and replay retained inbox files by SHA. Expected gain: crash-safe updates and explicit recovery. Risk: the importer may mishandle legacy rows or live changes during snapshot; verify hashes at start/end, import into a new DB, and rehearse restore before switching writers. Backup frequency and retention are design recommendations, **INFERRED**, not existing practice.

## 5. Cost and migration work

**Measurement.** `python3 scripts/cost_baseline.py` measured the current README bootstrap record output for six sources named at `README.md:7-12`: `status.py` 7,723 bytes; open pending query 8,741; last 10 decisions 2,962; all feedback 11,507; process lessons plus 10 other lessons 9,206; `state.json` 16,406; total 56,545 bytes.
