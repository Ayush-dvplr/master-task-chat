## 3. Draft design and Ayush steps

`scripts/verify_manifest.py` is a **DRAFT**, not installed. It discovers the protected set, computes canonical JSON SHA-256 values, verifies `ssh-keygen -Y verify` with identity `ayush-tb-master` and namespace `tb-master-rules-v1`, then compares exact current bytes. It rejects absent files, unexpected selected files, symlinks within selected trees, invalid signatures, and hash changes. `scripts/approve.sh` is a **DRAFT**: it creates a candidate, prints changed path/hashes, asks Ayush to type `APPROVE`, invokes `ssh-keygen -Y sign` (which asks for the key passphrase), verifies the candidate, then installs manifest/signature in a protected directory. The scripts created no key and made no installation or live rule change.

**Once, after S2 path layout is settled:** (1) Ayush creates a separate non-admin `tb-master` macOS account and decides its writable state/output paths; the account cannot write protected rules, trust files, signing key, or launcher. (2) As Ayush, run `ssh-keygen -t ed25519 -a 100 -f <Ayush-only private key path> -C tb-master-rules` and enter a strong passphrase; do not load this key into the master's `ssh-agent`. (3) Put `ayush-tb-master <public-key-line>` in Ayush/root-owned `allowed_signers`; install reviewed verifier and fixed-argument launcher in an Ayush/root-owned path outside the master repo. (4) Review every file in the first candidate inventory against the agreed baseline, then run the installed `approve.sh` with `TB_ROOT`, `AYUSH_HOME`, `TRUST_DIR`, `SIGNING_KEY` set to those fixed locations. (5) Launch master/auto only through the trusted wrapper: verify before OpenCode starts, after resume/compaction, before `issue.py`, before `auto.py` start/resume/spawn/send/harness, and before interpreting changed rule files. Refuse and report path names on any failure. Bootstrapping a pre-existing modified tree without reviewing it would sign the bad state.

Concrete commands for steps 2-4, **after** creating `tb-master` and reviewing/installing these drafts as Ayush (these commands are proposals, not run here):

The last command is also Ayush's **per-change approval command**, after he has reviewed and applied the proposed diff. The fixed-argument launcher is still a design item; it must call `/Users/mac/.tb-master-trust/verify_manifest.py verify --tb '/Users/mac/Desktop/Terminal Bench' --home '/Users/mac' --manifest /Users/mac/.tb-master-trust/manifest.json --signature /Users/mac/.tb-master-trust/manifest.json.sig --allowed-signers /Users/mac/.tb-master-trust/allowed_signers` and exit on any nonzero result. If `state.json` or another currently mixed config/state file needs master writes, split its mutable state out before setting ownership; otherwise existing behavior may stop.

**Per change:** master writes a proposal/diff in a writable staging area; Ayush reviews the content and copies the approved edit into protected files as owner; Ayush runs installed `approve.sh`, enters the key passphrase and checks the printed changed paths; only then does the master resume through the trusted wrapper. For an auto plan, Ayush approves the source plan before unattended start; `auto.py` must hash-check its copied `runs/<stamp>/PLAN.md` against that approved source. If an active run sees any protected-rule mismatch, it stops new actions and records `Needs Ayush`; existing workers can finish but their results are not accepted under the changed rules until verification succeeds.

**Risk/verification.** The draft does not protect itself while it sits in this OUT folder. It must be reviewed and installed outside master write access. `approve.sh` shows hashes and paths, so Ayush must inspect the actual content diff before typing `APPROVE`. A same-user unrestricted process can bypass a voluntary verifier. A separate non-admin account and a controlled launch path are the enforcement boundary. Static hash checks have a time-of-check/time-of-use race if another privileged process changes rules between checks; protect the files with permissions and recheck at action boundaries.
