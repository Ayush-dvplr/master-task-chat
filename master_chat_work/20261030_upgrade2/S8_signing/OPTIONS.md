# S8 approval options (draft, 30 Oct 2026)

The local check found `ssh-keygen -Y sign` and `-Y verify` in the command's usage output; `git --version` returned `2.54.0 (Apple Git-157)`; `command -v gpg` returned no path. `/usr/bin/chflags` exists. These are local command outputs from this session, not a claim that signing has been configured.

| Option | What stops the master | Ayush's per-change action | Failure modes and startup refusal |
|---|---|---|---|
| (a) SSH-signed SHA-256 manifest | Signature cannot be forged if the private key is inaccessible. A trusted verifier compares the *complete discovered file set* and hashes before use. | Inspect the proposed diff, run `approve.sh`, enter the SSH key passphrase at a local terminal. | Same-user master can edit/skip a verifier or use a key exposed through `ssh-agent`; wrong scope misses files; removed/added files must be detected. Put verifier, signer allowlist and approved manifest outside master write access. Reject missing/bad signature, hash/membership mismatch, symlink, or verifier error at launch and action boundaries. |
| (b) Git signed commits/tags + protected private repo | Remote branch protection can block an unsigned or unreviewed *merge* if configured on the new private GitHub repo. | Sign and push each change, approve merge; pull an approved ref. | A signed commit only authenticates the signer, not Ayush's review unless only his key counts. Local worktree can change after checkout; branch protection does not govern local reads. No repo exists at `master_chat_tasks` now (`git rev-parse --show-toplevel` returned “not a git repository”). Git 2.54 supports signing, but no signing configuration was verified. Startup must validate approved commit/ref **and** a clean exact worktree, plus external config/skills outside the repo. |
| (c) macOS `uchg`/permissions or separate user | `uchg` and ownership/ACLs can prevent a non-admin master account writing protected files; a separate non-admin account gives a real OS boundary. | Unlock/allow owner write with password, edit, then relock; or Ayush edits files as owner and reruns approval. | Same `mac` user owns today's rule files (`ls -ldO` showed `mac staff`, flag `-`), so same-user `chmod`/`chflags` is not a strong boundary. Admin/sudo or a leaked password can bypass. Permissions alone do not prove which content Ayush approved. Startup should also run (a). |
| (d) Manifest + Ayush-run passphrase script | Only if the passphrase is processed outside the master's account and the verifier/manifest are protected. | Enter passphrase into `approve.sh` for each change. | A custom password check is easy to bypass or leak; plain hash manifest can be rewritten by the master. A password-derived MAC needs secret handling and key derivation; it duplicates standard SSH signing. Refuse at startup on absent/invalid approval, but same-user bypass remains. |

**Recommendation:** combine (a) with (c)'s separate non-admin master account. The signing key stays under Ayush's account and is never added to that account's `ssh-agent`; the installed verifier, launcher, signer allowlist and signed manifest are Ayush/root owned. The master account gets read access to protected rules and write access only to task state/output areas. The signed manifest authenticates exact bytes; permissions prevent edits. Git from S2 is a review/history and distribution layer, not the trust root.

**Limits:** No code-only guard can force an arbitrary process running as the same unrestricted `mac` user to call a verifier. A trusted launch path plus OS separation is required to make “must not be able” credible. Runtime package code under `~/.config/opencode/node_modules/` is not included in the draft scope; pin/version-lock it or expand the manifest if the master can change installed plugin code. The script also does not prove that an issued prompt has not inserted a new standing rule. `issue.py` needs template provenance and validated substitution fields before that claim can be made.
