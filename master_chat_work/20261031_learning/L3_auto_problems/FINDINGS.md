## 3. Polling and Docker waits

**Finding.** Across the 93 auto-linked SHA sessions, `OUT/POLL_STATS.csv` has **987 sleep-bearing tool calls**, **2,183.7 summed tool minutes (36.4 h)**, **240 sleep calls containing `docker ps`**, and **40 exact consecutive repeat sleep calls** (command: `python3 OUT/scripts/audit_sessions.py`, filter `auto_runs != ''`, sum columns). These are overlapping session/tool times, not 36.4 hours recoverable from one calendar night. The prior, broader 164-session study used a narrower poll definition and measured 55.5 h / 23% of aggregate session time, with 382 `sleep ...; docker ps` calls on 26-30 Oct (`master_chat_work/20261030_speed_measure/MEASURE.md:79-108`). The CSV's `explicit_slot_wait_calls` is a conservative text-in-same-message signal, **not a complete slot-wait count**; 733 calls had own-job context and 236 were unclear by that heuristic (script `audit_sessions.py:43-60`).

**Slot versus own job.** ed621c7 explicitly waited for *another session's* container before launching its first own one: 09:19 to 11:01, at least 102 minutes, with 29 Docker samples and only 1-2 foreign containers (prior primary DB review in `MEASURE.md:123-132`; `POLL_STATS.csv:127` has 48 sleeps, 108.0 min, 37 containing `docker ps`). Cold-chain had a separately logged 5 m 47 s wait for a nop slot (`MEASURE.md:132-134`). By contrast ac12c0b, cc541be, 361674d, and 4989b35 repeatedly tailed **their own** Step 10/scoring logs while detached chains ran (`opencode.db` commands reproduced by `OUT/scripts/timeline.py`; `POLL_STATS.csv:79,108,131,166`; `auto/runs/20261028T1553_evening/REPORT.md:42,49`). The identical `sleep 235; date; tail...` call was denied three times in ac12c0b's transcript at 16:53, and the same pattern recurred for cc541be at 06:43; the guard stopped the assistant but not the chain (`events.jsonl` citations above).

**What a blocking wait would save.** A single event/log-completion wait **per background phase** could replace repeated assistant-issued `sleep; tail` calls and eliminate the exact-call guard exposure. It would not shorten the underlying Harbor/verifier runtime, so **wall-time saving is UNVERIFIED**; the observed 36.4 h is only an upper bound on tool occupation across concurrent sessions. A `docker events` wait for a *foreign* slot is insufficient by itself: ed621c7 was obeying a social serial rule even with 1-2 containers up; it needs shared capacity admission/lease rather than another poll mechanism (`MEASURE.md:123-134`, `S6_auto_speed/FINDINGS.md:31-35`). Check with a simulated 20-minute log writer: compare worker tool calls, end-to-end completion, correct exit/status capture, and a stale/missed event fallback. A too-long blocking call can hit tool timeout or hide a dead process; use a bounded wait plus heartbeat/fallback.

## 4. Watcher coverage and gaps

**Finding.** Current `auto.py` polls at 60 s, calls `poll_workers`, `poll_harness`, `check_limit`, then delivers events (`auto.py:68-79,1894-1945`). `poll_workers` treats server `retry` separately, waits two idle polls before `handle_result`, and reads passive adopted sessions through DB (`auto.py:1401-1455`). `check_limit` recognizes worker/MQ usage limits, holds new work and the queue, notifies, and clears after two clean polls (`auto.py:1515-1589`). `handle_doom` sends one corrective continue, then blocks a second guard stop (`auto.py:1376-1398`). `note_master_hold` alerts only when queued watcher events meet a master in provider retry for two polls; it deliberately ignores a merely busy master (`auto.py:1767-1792`). These cover the later doom episode and status-visible limits, but the 27 Oct smoke run shows the older watcher missed an internally retrying, apparently BUSY session (`REPORT.md:14-17`); **production efficacy of the current retry status path remains UNVERIFIED**.

`check_stall` emits only when **every** active owned worker's newest activity is older than 20 minutes; its activity clock includes last send, last assistant message, and latest OUT mtime (`auto.py:1480-1512`). A single idle worker beside active peers is invisible. `check_gap` detects watcher silence over 10 minutes only when the watcher gets another poll (`auto.py:1712-1718`); it could have reported both shared freezes after 02:50 and 07:50, but could not wake the watcher while it was silent. The old run produced neither stall nor gap event during its 05:00-07:50 freeze (`REPORT.md:30,80,88`). The current `poll_workers` also reports an idle assistant as `done` after two polls without consulting a detached-job manifest (`auto.py:1431-1445`), and `handle_result` marks a nonerror response done without verifying the expected deliverable (`auto.py:1346-1358`). `ContextOverflowError` falls into the generic nonretry error path (`auto.py:553-565,1359-1367`); 6740572 needed an external continuation.

**Exact catch rules.** (a) If an owned worker has no new assistant tool start/completion **and** no OUT or job heartbeat for 20 minutes while its expected deliverable is missing, emit `WORKER_STALL <sha>` even when other workers progress; do not flag a known live long tool or a job whose heartbeat advances. (b) If an idle/errored worker has a verified child manifest entry still alive, emit `JOB_RUNNING_WITH_IDLE_WORKER`, preserve the job, and defer `done` until the completion sentinel/result is read. (c) If a worker is `busy` with an empty assistant for two polls and the worker-server retry state or local provider log identifies a limit, apply `LIMIT`; otherwise emit `UNKNOWN_RETRY` without holding the queue. (d) On `ContextOverflowError`, emit `CONTEXT_STOP` and allow one checkpoint-based continuation after re-reading TODO/LOG; a second error stops. (e) On `check_gap` over 10 minutes, record the exact elapsed gap and all workers with missing deliverables before any wind-down decision; an **independent** watchdog is needed if detection must occur while `auto.py` itself is silent. Each rule is narrower than “busy for a long time” and maps respectively to the individual stall blind spot, orphan jobs, smoke retry, 6740572, and the two shared freezes.

**What to change / expected gain / risk / check.** Implement the rules near `auto.py:1401-1512,1712-1718,1894-1945`. Expected gain: minutes to hours of earlier detection when the watcher is alive, and accurate post-gap accounting; no guaranteed rescue while the whole runtime is paused. Risks: false alerts on legitimate long tools, stale file mtimes, and duplicate continuations. Replay the saved DB/event timelines with a fake clock: one live worker plus one 21-minute idle worker must alert; a heartbeat job must not; the 23:19 and 04:59 gaps must each yield one GAP on return; the 6740572 error must continue once only; retry clean-up must leave the queue held until two clean polls. External watchdog installation is a separate operational decision.
