# Final reply — hangar-check-replan

**What I built.** `derive_report.py` (Python 3 stdlib only), shipped at `app/derive_report.py` and `out/derive_report.py`, run as `python3 derive_report.py --data <data dir> --out <out dir>` with the instruction's `/app` defaults. It reads the whole data folder with small hand-written parsers (flat TOML, two-level YAML, the markdown disruption notice, CSV, JSONL), filters the request file to the configured season with status OPEN, and rejects bad rows in the documented order (`unknown_base`, `unknown_tail`, `retired_tail`, `unknown_check_type`, `bad_date`, `bad_duration`, `no_published_start`, `duplicate_request`), recording file line numbers. It then solves the replan exactly: one hangar line per base, each check occupying consecutive open days with no closed day inside the window, compression limited by the check type and paid out of the shared overtime pool, deferral allowed when nothing fits. Per base a memoised DP over (remaining requests, first free day) returns, for every exact number of overtime shifts, the best plan as a lexicographic triple (the three plan terms packed into one integer, then the start-day vector, then the finish-day vector); the top level distributes the pool across the four bases, keeps every split tied on the summed objective, and breaks the tie by the globally smallest start vector then finish vector in request_id order. Outputs: `check_plan.json`, `regions/region_{north,south,west,east}.json`, `segments/segment_{commercial,public}.json`, `plan_summary.json`, `data_quality.json`.

**What I checked.** One run on the shipped data under the wall-clock cap: exit 0, **0.12 s real** (limit 60 s), nothing on stderr, all 7 files present with the schema's field names and ordering. Then an independent re-derivation (`work/selfcheck.py`, 0.04 s, `ERRORS: none`) recomputed everything from the data folder: membership and sorting of the 21 surviving checks, every per-check field, `finish − start + 1 = duration − compress_days`, compression caps, shifts per compressed day, tail availability including the four revised dates, no start on a closed or NO_START day, no closed day spanned, finish inside the season, no two checks sharing a day on one base line, overdue days, `moved` against the published plan, the deferral reason re-derived on an empty line, the pool total, and every aggregate in the region, segment and summary files, plus the data-quality counts.

**Key figures.** 29 in-season OPEN rows → 8 rejected (exactly one per reason, lines 103/689/784/1207/2219/4107/4494/4714) and 21 planned: **20 scheduled, 1 deferred** (`Q87483`, narrowbody D-check at South, reason `no_slot` — the South closure 2027-04-13..04-21 plus five other South checks leave no 14-day window), **5 moved** off their published start. Plan terms: 130 / 9670 / 5. Overtime: **82 of the 82 pool shifts used** — North 12, South 24, West 18, East 28. Segments: commercial 15 scheduled / 0 deferred, public 5 scheduled / 1 deferred.

**Caveat.** The optimiser is exact for the data shapes shipped here (four bases, ≤6 requests per base, 120-day season); the per-base DP is exponential in requests per base, so a folder with many more requests on one base would need the candidate-start set widened rather than the search re-tuned.
